AWS · Identity & Access Management

IAM is the front door
every other service checks.

IAM doesn't store your data, run your compute, or route your traffic — it decides who is allowed to touch the services that do. Every API call anywhere in AWS is first stopped and asked for ID. This guide covers what IAM actually is, how it wires into the rest of the AWS service graph, when to reach for which primitive, and the production patterns (and interview questions) that separate "I've used IAM" from "I understand IAM."

01 · Definition

What IAM actually is

IAM (Identity and Access Management) is AWS's global, free authentication and authorization service. It answers two questions on every single request made to AWS, whether it comes from the console, the CLI, an SDK, or another AWS service: "who are you?" (authentication) and "what are you allowed to do?" (authorization).

It is not tied to a region — IAM is a global service. A user or role you create is visible and usable from every region simultaneously. IAM itself doesn't do anything to your resources; it only evaluates policy documents and returns Allow or Deny before the target service (S3, EC2, Lambda, etc.) is permitted to execute the request.

Mental model

Think of every AWS API call as a locked door. IAM is the security guard standing in front of every door in AWS — S3 buckets, EC2 instances, Lambda functions, RDS snapshots, everything. The guard doesn't own the room; it just checks the badge (identity) against the access list (policy) before letting the request through.

02 · Building blocks

Core concepts

Five primitives make up almost everything you do in IAM. Understanding how they compose is more important than memorizing any one of them.

IDENTITY

User

A persistent identity for a person or application. Has long-lived credentials (password, access keys).

Use when you have a real human who needs console access, or a genuine standalone identity that isn't running inside AWS compute.
IDENTITY

Group

A named collection of users. Policies attached to a group apply to every member. Not a true identity — can't be assumed or referenced in a policy's Principal.

Use when managing permissions for teams (e.g. "Developers", "Billing-Admins") instead of per-user.
IDENTITY

Role

A temporary identity with a trust policy defining who/what can assume it, and a permissions policy defining what it can do once assumed. No long-lived credentials.

Use when AWS services need permissions (EC2, Lambda), for federation/SSO, or cross-account access.
DOCUMENT

Policy (JSON)

A document of statements — Effect, Action, Resource, optional Condition — that grants or denies specific API actions on specific resources.

Use when defining exactly what an identity can do. Managed (reusable) or inline (one-to-one).
SERVICE

STS

Security Token Service — issues short-lived credentials (typically 15 min–12 hr) when a role is assumed via AssumeRole, AssumeRoleWithSAML, or AssumeRoleWithWebIdentity.

Use when any cross-account access, federation, or service-to-service call happens — this is the engine behind roles.
SCOPE

Resource-based policy

A policy attached directly to a resource (S3 bucket policy, KMS key policy, Lambda resource policy) rather than to an identity. Defines who can access that resource, from any account.

Use when granting access from a different AWS account without assuming a role in your account.
Policy evaluation order

An explicit Deny always wins, regardless of how many Allows exist elsewhere. If no explicit statement matches, the default is implicit Deny. Final decision = evaluate every applicable identity-based policy, resource-based policy, permissions boundary, SCP (Organizations), and session policy together — the request is allowed only if nothing in that whole set denies it and at least one thing allows it.

04 · Detail

Service-by-service: how the connection actually works

EC2

An EC2 instance never holds AWS credentials as files. Instead you attach an instance profile (a wrapper around an IAM role) to the instance. The instance metadata service (IMDS) hands the OS temporary STS credentials automatically, refreshed continuously. This is how an app on the box calls S3 or DynamoDB without a single hardcoded key.

Lambda

Every function has exactly one execution role. IAM grants the function permission to write to CloudWatch Logs, and separately whatever downstream permissions it needs (e.g. dynamodb:PutItem). The trust policy on the role must allow lambda.amazonaws.com to assume it, or the function fails to even start.

S3

S3 is checked twice: the caller's identity-based policy (does the user/role have s3:GetObject?) and the bucket's own resource-based policy (does the bucket allow this principal?). Cross-account S3 access is the classic case where the bucket policy does the heavy lifting instead of a role.

KMS

Every KMS key has a key policy that is the root authorization — even an admin with full IAM permissions can't use a key unless the key policy also allows it. This is intentional: it's the one place where IAM alone is not sufficient, by design, to prevent a compromised IAM admin from silently granting themselves decrypt access.

CloudTrail

Records every IAM-mediated API call — who (identity), what (action), when, from where (source IP), and the result (allow/deny). It's the audit trail that makes IAM decisions forensically reviewable, and it is itself protected by IAM permissions on who can read or disable it.

Organizations

Service Control Policies (SCPs) apply at the account/OU level and set the outer boundary — they never grant permissions, only restrict the maximum an account can ever allow, no matter what an in-account IAM policy says. A permissive IAM policy inside an account still fails if an SCP denies it above.

EKS (IRSA)

Kubernetes pods assume IAM roles via IAM Roles for Service Accounts — an OIDC identity provider trust relationship maps a Kubernetes service account to an IAM role, so individual pods get scoped, short-lived AWS credentials instead of the whole node sharing one broad role.

STS / Cognito / SSO

STS is the credential-issuing engine behind every role assumption. Cognito Identity Pools and IAM Identity Center (SSO) both federate an external identity (a corporate directory, a social login, a SAML IdP) into a temporary STS-issued IAM role session — no IAM user is ever created for the end human.

05 · Principle

Least privilege, in practice

Least privilege means granting exactly the permissions required to perform a task — no more. It's the single most-repeated IAM principle because violating it is the single most common root cause of AWS security incidents (leaked keys with admin access, an over-permissioned Lambda reading a whole account's S3 data, etc.).

How to actually implement it

  • Start from zero, not from Admin. Begin with an empty policy and add actions as they're proven necessary, rather than starting broad and trying to trim later (trimming almost never happens).
  • Use IAM Access Analyzer's policy generation. Point it at CloudTrail logs for an identity over 90 days and it will generate a policy containing only the actions actually used.
  • Scope the Resource field. Avoid "Resource": "*". Restrict to specific ARNs — a specific bucket, a specific table, a specific key — not the whole service.
  • Add Conditions. Restrict by source IP (aws:SourceIp), MFA presence (aws:MultiFactorAuthPresent), time window, or requested region to shrink the blast radius even for an allowed action.
  • Use permissions boundaries for delegated admin. If you let a team create their own roles, a permissions boundary caps the maximum permission any role they create can ever have.
  • Review with Access Analyzer continuously. It flags unused permissions and external-account access on an ongoing basis, not just at creation time.
  • Prefer roles over long-lived user keys everywhere possible. A role's credentials expire on their own; a leaked access key doesn't expire until someone notices and rotates it.
Anti-pattern

"Action": "s3:*", "Resource": "*" attached to an application role because it was faster than figuring out the three actions it actually needed.

Least privilege

"Action": ["s3:GetObject","s3:PutObject"], "Resource": "arn:aws:s3:::app-uploads-bucket/*" — scoped to the exact bucket and the exact two actions the app calls.

06 · Decision guide

When to use what

SituationUseWhy
A human needs console/CLI access IAM Identity Center (SSO) Federated, centrally managed, short-lived sessions — avoids standing IAM users entirely. Fall back to an IAM user only for legacy cases.
An AWS service needs to act on your behalf IAM Role No credentials to store or rotate; the service assumes the role and STS issues temporary creds automatically.
Cross-account access (e.g. central logging account) Role + trust policy or resource policy A role in Account B trusts Account A's principal; or the resource (bucket, key) in Account B grants Account A directly.
A third-party SaaS needs limited access to your account Role + External ID condition Prevents the "confused deputy" problem — the external ID must match or the assumption fails, even if the role ARN leaks.
A CI/CD pipeline (e.g. GitHub Actions) needs to deploy OIDC federation to a role No long-lived AWS keys stored as CI secrets at all — the pipeline exchanges its own OIDC token for temporary AWS credentials.
You need to grant the same permission set to many users Group Attach the policy once to the group; add/remove members instead of managing permissions per user.
You need an org-wide guardrail no account can override SCP (Organizations) Sets a hard ceiling below which even an account's own Administrator can't grant more, e.g. "never allow leaving the org's approved regions."
One-off, narrow permission tied to a single resource Inline policy Lives and dies with the identity — no risk of an orphaned managed policy being reused somewhere unexpected.
Reusable permission set across many identities Customer-managed policy Versioned, attachable to many roles/users/groups, and centrally auditable — the standard for production.
07 · Operations

Production-level checklist

What experienced AWS teams actually enforce day to day — this is the list an interviewer is hoping you'll bring up unprompted.

  • Root account is locked down. MFA enabled (hardware key ideally), no access keys ever generated, used only for the handful of tasks that truly require root.
  • No standing IAM users for humans. Access goes through IAM Identity Center / federated SSO with short-lived sessions.
  • MFA enforced everywhere it's supported, and sensitive actions gated behind a aws:MultiFactorAuthPresent condition.
  • Access keys, if they must exist, are rotated on a schedule and monitored by IAM Access Analyzer / Credential Reports for staleness.
  • Multi-account structure via AWS Organizations, with SCPs as the outer guardrail, not single-account IAM sprawl.
  • Every policy is scoped with explicit Resource ARNs and Conditions — wildcards are a flagged exception, not the default.
  • CloudTrail is on in every account and region, delivered to a centralized, access-restricted logging account, with log-file validation enabled.
  • Permissions boundaries used for any self-service role creation (e.g. a platform team letting app teams create their own roles).
  • Break-glass access is documented and tested — an emergency admin path that's audited and alerted on every time it's used.
  • Regular access reviews — unused roles, unused permissions, and stale users get flagged and removed, not left "just in case."
08 · Reference

A least-privilege policy, annotated

A role for an application that only needs to read from one S3 prefix and write logs — nothing else.

app-read-only-policy.json 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadOnlyUploadsPrefix",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::prod-app-uploads",
        "arn:aws:s3:::prod-app-uploads/reports/*"
      ],
      "Condition": {
        "StringEquals": { "aws:PrincipalOrgID": "o-exampleorgid" },
        "Bool": { "aws:SecureTransport": "true" }
      }
    },
    {
      "Sid": "WriteOwnLogs",
      "Effect": "Allow",
      "Action": "logs:PutLogEvents",
      "Resource": "arn:aws:logs:*:111122223333:log-group:/app/prod:*"
    }
  ]
}

Notice: no * resources, an explicit prefix, a transport-security condition, and an org-membership condition — three independent narrowing mechanisms stacked on top of the base action grant.

09 · Interview Prep

Interview questions & answers

Ordered roughly easy → hard. Click to expand.

Q1What's the difference between an IAM user and an IAM role?Easy▸

A user is a permanent identity with long-lived credentials (password and/or access keys) meant for a specific person or app. A role has no permanent credentials — it's assumed, and STS issues temporary credentials that expire. Roles are the preferred mechanism for anything that can assume one: AWS services, federated humans, cross-account access, and CI/CD.

Q2What happens when an Allow and a Deny both apply to the same request?Easy▸

Deny always wins. IAM's evaluation logic is: start with implicit deny, look for any explicit Deny across all applicable policies (identity, resource, SCP, permissions boundary, session policy) — if found, deny immediately regardless of any Allow. Otherwise, allow only if at least one explicit Allow exists.

Q3Why is IAM described as a "global" service rather than regional?Easy▸

IAM identities, policies, and roles aren't created per-region — they exist account-wide and are usable from any region without replication. This is different from most AWS services (EC2, RDS, S3 buckets to a degree) which are regional or have regional endpoints.

Q4Explain the difference between an identity-based policy and a resource-based policy.Medium▸

An identity-based policy is attached to a user, group, or role and defines what that identity can do. A resource-based policy is attached directly to a resource (S3 bucket, KMS key, SQS queue, Lambda function) and defines who can access that specific resource — critically, it can grant access to a principal in a different AWS account without that account needing to assume a role in yours. S3 bucket policies and KMS key policies are the two most common examples.

Q5How would you grant a Lambda function in Account A access to an S3 bucket in Account B?Medium▸

Two pieces are both required: the Lambda's execution role in Account A needs an identity-based policy allowing s3:GetObject on the bucket's ARN, and the bucket policy in Account B needs a statement allowing Account A's role ARN as a principal. Either one alone is insufficient — cross-account access needs both sides to agree.

Q6What is a permissions boundary and how is it different from a regular policy?Medium▸

A permissions boundary is an advanced feature that sets the maximum permissions an identity-based policy can grant to a user or role — it never grants permissions by itself, only caps them. It's typically used when delegating role/user creation to a team: even if that team writes an overly broad policy, the boundary prevents it from exceeding the ceiling you set.

Q7What's the difference between a Service Control Policy (SCP) and an IAM policy?Medium▸

An SCP is applied at the AWS Organizations level (account or OU) and, like a permissions boundary, only restricts — it never grants. It sets the outer limit for every identity in every account under it, including that account's own root user and admins. An IAM policy is applied inside a single account and can actually grant permissions, but only within whatever ceiling the SCP above it allows.

Q8How does an EC2 instance get AWS credentials without anyone hardcoding them?Medium▸

You attach an instance profile (which wraps an IAM role) to the instance. The Instance Metadata Service (IMDS) running on the instance exposes temporary STS credentials at a local endpoint, which the AWS SDK automatically discovers and refreshes before they expire — typically every few hours. Nothing is written to disk as a static key.

Q9Why can't an IAM administrator automatically decrypt data protected by any KMS key?Hard▸

KMS key policies are the root of authorization for a key and are evaluated independently of standard IAM logic — even a user with iam:* and kms:* permissions cannot use a key unless the key's own policy grants that principal (or grants IAM policies the right to govern it, if the key policy delegates that). This is a deliberate separation-of-duties control so that compromising IAM administration alone doesn't automatically expose all encrypted data.

Q10What's the "confused deputy" problem and how does IAM address it?Hard▸

It's when a third party is tricked into misusing its own legitimate permissions on your behalf — e.g. a SaaS vendor has a role in your account, and an attacker who knows that role's ARN convinces the vendor's system to assume it against a different, unintended customer. IAM addresses this with the sts:ExternalId condition: you generate a unique external ID and require it in the trust policy, so a role assumption request without the correct external ID fails, even with the right role ARN.

Q11Walk through what happens, step by step, when a federated user logs in via SSO and calls an AWS API.Hard▸

The user authenticates against the external identity provider (Okta, Azure AD, etc.). The IdP issues a SAML assertion or OIDC token. IAM Identity Center (or a direct SAML/OIDC trust) validates that token and calls STS's AssumeRoleWithSAML or AssumeRoleWithWebIdentity. STS checks the role's trust policy to confirm the IdP is trusted, then issues temporary credentials (access key, secret key, session token) scoped to that role's permissions policy. The user's CLI/SDK uses those temporary credentials for the API call, which IAM evaluates against the role's permissions exactly as it would for any other identity.

Q12How would you design least-privilege access for a CI/CD pipeline that deploys to production?Hard▸

Avoid static AWS keys stored as CI secrets entirely — configure OIDC federation between the CI provider (e.g. GitHub Actions) and an IAM role, so the pipeline exchanges a short-lived OIDC token for temporary STS credentials on every run. Scope the role's trust policy with a condition restricting it to a specific repo and branch, scope the permissions policy to exactly the deploy actions and resources needed (e.g. specific CloudFormation stack, specific S3 deployment bucket), and separate roles per environment so a compromised staging pipeline can't touch production.
