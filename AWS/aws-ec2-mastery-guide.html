01

What is EC2?

Amazon EC2 (Elastic Compute Cloud) is AWS's core Infrastructure-as-a-Service offering: on-demand, resizable virtual servers ("instances") that run in AWS data centers instead of your own hardware. You pick an operating system image, a hardware profile (CPU/RAM/network), storage, and networking, and AWS boots a virtual machine for you in seconds.

Why AWS created it: before EC2 (launched 2006), running a server meant buying physical hardware, waiting weeks for procurement, and over-provisioning for peak load you'd rarely hit. EC2 solved this by letting compute be requested and released like any other metered utility.

Problem it solves: capacity planning, hardware procurement lead time, idle-hardware waste, and the inability to scale down. EC2 turns capital expenditure (buying servers) into operational expenditure (renting compute by the hour/second).

Where it fits in AWS architecture: EC2 is the general-purpose compute layer. Higher-level compute services (Lambda, ECS, EKS, Elastic Beanstalk) are either built on top of EC2 under the hood or exist as an alternative to it for narrower use cases.

Beginner explanation

It's a computer that lives in Amazon's data center that you rent by the hour. You get to choose how powerful it is, what operating system it runs, and you can turn it on, off, or delete it whenever you want.

Technical explanation

A Xen/Nitro-hypervisor-backed virtual machine instance, launched from an AMI, scheduled onto a physical host within an Availability Zone, attached to EBS/instance-store volumes and an ENI inside a VPC subnet, governed by IAM (via instance profile), security groups, and billed per-second based on instance type.

Real-world analogy

EC2 is like renting a fully furnished apartment instead of building a house. You don't own the building (physical hardware), you choose a floor plan (instance type), you can move out or upsize any time (resize/terminate), and the landlord (AWS) handles the plumbing and electricity (power, cooling, physical security, hypervisor).

When NOT to use it

  • Short, event-driven, bursty workloads — Lambda avoids paying for idle servers and removes patching entirely.
  • You don't want to manage an OS at all — Fargate (ECS/EKS) or Lambda remove the instance layer.
  • Pure static content hosting — S3 + CloudFront is cheaper and has no servers to patch or scale.
  • Fully managed database needs — RDS/Aurora/DynamoDB instead of self-managing a DB on EC2.

Three real-world examples

ExampleWhy EC2
Netflix encoding fleetLarge, variable-size fleets of compute-optimized instances for video transcoding, scaled with Auto Scaling based on queue depth.
A fintech's core transaction APINeeds full OS-level control, specific compliance-approved AMIs, and predictable performance — run behind an ALB across multiple AZs.
A startup's self-hosted Jenkins/GitLabNeeds persistent, stateful compute with root access and custom tooling that doesn't fit a managed/serverless model.
02

Core concepts

1. AMI (Amazon Machine Image)

Simple: a template/snapshot used to launch an instance — OS plus any pre-installed software. Technical: a combination of a root volume snapshot, launch permissions, and a block device mapping registered in a region. Why it exists: to make launches reproducible and fast instead of installing an OS from scratch every time. Use case: baking a "golden AMI" with your hardened OS, agents, and app runtime pre-installed so Auto Scaling can launch identical instances in seconds. Common mistake: forgetting AMIs are region-specific and not copying them to every region you deploy in. Interview Q: "How would you keep AMIs consistent and patched across 50 instances?" → golden AMI pipeline with EC2 Image Builder, rebuilt on a schedule.

2. Instance type & family

Simple: the "size" of virtual hardware — CPU, RAM, network, sometimes GPU. Technical: a fixed combination of vCPU count, memory, network performance tier, and sometimes local NVMe storage, named by family+generation+size (e.g. m6i.large). Why it exists: different workloads need different CPU:RAM:network ratios — a single "one size" instance would be wasteful for most use cases. Use case: c-family (compute-optimized) for CPU-bound batch jobs, r-family (memory-optimized) for in-memory caches/databases, m-family (general purpose) for typical web apps. Common mistake: defaulting to t2/t3 burstable instances for sustained high-CPU workloads and getting CPU-credit throttled. Interview Q: "Why did your app slow down after running fine for an hour?" → CPU credit exhaustion on a burstable instance type.

3. EBS (Elastic Block Store)

Simple: a virtual hard drive that attaches to your instance and persists independently of it. Technical: network-attached, AZ-locked block storage replicated within the AZ, available in gp3/gp2 (SSD general purpose), io1/io2 (provisioned IOPS SSD), st1/sc1 (HDD) types. Why it exists: instance store (local disk) is ephemeral — data is lost on stop/terminate/hardware failure; EBS decouples storage lifecycle from instance lifecycle. Use case: the root volume of nearly every production instance, plus separate data volumes for databases. Common mistake: assuming EBS survives across AZs — it doesn't; you must snapshot and restore into another AZ. Interview Q: "EBS vs instance store — when would you actually choose instance store?" → when you need very high local IOPS and the data is fully disposable/replicated elsewhere (e.g. Kafka log segments, cache nodes).

4. Security Groups

Simple: a virtual firewall attached to the instance's network interface. Technical: stateful, allow-only rule sets evaluated at the ENI level — return traffic for an allowed request is automatically permitted regardless of outbound rules. Why it exists: to control exactly which traffic reaches an instance without needing OS-level firewall configuration for basic segmentation. Use case: allowing inbound 443 only from an ALB's security group, not from 0.0.0.0/0. Common mistake: opening SSH (22) to 0.0.0.0/0 "temporarily" and forgetting to close it. Interview Q: "Security Group vs NACL?" → SG is stateful and instance-level (allow-only); NACL is stateless and subnet-level (allow + deny).

5. Key Pairs

Simple: the SSH key used to log into a Linux instance (or decrypt the Windows admin password). Technical: asymmetric key pair; AWS stores only the public key, injected into ~/.ssh/authorized_keys at first boot via cloud-init. Why it exists: password-based SSH is weak by default; key-based auth is the AWS-native secure bootstrap mechanism. Use case: initial access to a freshly launched instance before configuration management takes over. Common mistake: losing the private key with no recovery path except detaching the root volume and mounting it on another instance. Interview Q: "You lost the .pem file for a running instance — now what?" → stop instance, detach root EBS volume, attach to a rescue instance, edit authorized_keys, reattach, restart.

6. Elastic IP

Simple: a static public IP address you own that can be moved between instances. Technical: a public IPv4 address allocated to your account, associated to an ENI; unassociated EIPs incur an hourly charge specifically to discourage hoarding. Why it exists: a regular public IP changes every time you stop/start an instance — EIP gives DNS-stable addressing. Use case: a NAT instance, or a legacy app that's hardcoded to an IP rather than a DNS name. Common mistake: relying on EIPs instead of a load balancer + DNS for scalable production traffic. Interview Q: "Why would AWS charge you for an EIP that's not attached to anything?" → to discourage IPv4 address hoarding, since IPv4 space is scarce.

7. Instance metadata & IAM instance profile

Simple: a local, in-instance endpoint that gives the OS information about itself, including temporary AWS credentials. Technical: IMDS (169.254.169.254), now defaulting to IMDSv2 (session-oriented, token-required) to prevent SSRF-based credential theft; the instance profile wraps an IAM role whose STS credentials are exposed there. Why it exists: so applications never need hardcoded AWS keys. Use case: an app on the instance calling S3 using the SDK's default credential chain, which automatically finds IMDS-issued credentials. Common mistake: leaving IMDSv1 enabled, which is vulnerable to SSRF attacks that steal the role's credentials (as in the 2019 Capital One breach). Interview Q: "How do you prevent SSRF from stealing an instance's IAM credentials?" → enforce IMDSv2 (--http-tokens required), which requires a session token obtainable only via a PUT request that most naive SSRF proxies can't replicate.

8. Placement groups & Auto Scaling

Simple: placement groups control physical proximity of instances; Auto Scaling automatically adds/removes instances based on demand. Technical: placement strategies are cluster (low-latency, same rack), spread (max 7 per rack, isolate failure), and partition (grouped racks, for distributed systems like Cassandra/HDFS); Auto Scaling Groups (ASGs) maintain a desired count using launch templates and scaling policies against CloudWatch metrics. Why they exist: to optimize either for network latency (cluster) or fault isolation (spread/partition), and to remove manual capacity management entirely. Use case: an ASG behind an ALB scaling out on high CPU/request count, scaling in overnight to save cost. Common mistake: setting scaling thresholds too aggressively, causing "flapping" (rapid scale out/in cycles). Interview Q: "Your ASG keeps launching and terminating instances every few minutes — why?" → scaling policy thresholds too tight/no cooldown, causing oscillation around the threshold.

03

Architecture

EC2 instances live inside a Region → Availability Zone → VPC → Subnet hierarchy. A launch request flows through the control plane, gets scheduled onto a physical host by the placement engine, and boots via the Nitro hypervisor with attached ENI(s) and EBS volume(s).

Request (Console/CLI/SDK) │ ▼ [EC2 Control Plane] ── validates IAM permissions, quotas, AMI access │ ▼ [Placement Engine] ── picks a physical host in the target AZ │ ▼ [Nitro Hypervisor] ── boots the VM, attaches ENI + EBS │ ├──▶ [ENI] ──▶ Subnet ──▶ Route Table ──▶ IGW/NAT ──▶ Internet │ └──▶ [EBS Volume(s)] ──▶ EBS storage fleet (replicated within AZ) Instance boots → cloud-init runs → SSH key injected → user-data script executes → instance reachable

Step-by-step

  • Control plane validation: IAM checks you're allowed to run this instance type/AMI; service quotas checked (e.g. vCPU limit per region).
  • Placement: AWS's internal scheduler picks a physical host with capacity in your chosen AZ, honoring any placement group strategy.
  • Boot: the Nitro hypervisor allocates the VM, attaches the root EBS volume (or instance store) and a primary ENI inside your chosen subnet.
  • Bootstrap: cloud-init runs on first boot — injects your SSH public key, sets hostname, and executes any user-data script you supplied (common for installing an agent or pulling app code).
  • Network path: traffic in/out is governed by the subnet's route table, the instance's security group, and the subnet's NACL, before ever reaching an Internet Gateway or NAT Gateway.

Availability, scaling, fault tolerance

A single EC2 instance is not highly available by itself — it lives on one physical host in one AZ. High availability comes from architecture on top of EC2: multiple instances across multiple AZs, fronted by a load balancer, managed by an Auto Scaling Group that replaces unhealthy instances automatically. AWS's own resilience commitment is at the AZ/region level (physical redundancy, power, networking) — instance-level resilience is your responsibility.

Security boundaries

Layered from outside in: NACL (subnet, stateless) → Security Group (instance ENI, stateful) → OS firewall (iptables/nftables/Windows Firewall, if configured) → IAM (what the instance's role can do to other AWS services) → IMDSv2 (what can read the instance's own credentials).

What an interviewer expects you to know

That a single instance is a single point of failure by default, that AZs are physically isolated, that the shared responsibility model puts host/hypervisor security on AWS but OS/patching/app security on you, and that scaling is something you architect (ASG+ALB), not something EC2 gives you for free.

AWS Console walkthrough

Step-by-step to launch a production-sensible instance via the Console.

1. Name and OS image

Select: a tagged name and an AMI (e.g. Amazon Linux 2023). Why: Amazon Linux is patched by AWS and tuned for EC2. Behind the scenes: the AMI ID is resolved to a snapshot in the target region. Production rec: use a golden AMI, not the raw base image, once you have configuration to bake in. Security: only use AMIs from AWS, verified marketplace vendors, or your own account — never an untrusted community AMI. Cost: some marketplace AMIs carry an hourly software fee on top of instance cost.

2. Instance type

Select: e.g. t3.micro for testing, m6i.large for production web. Why: match vCPU/RAM ratio to workload. Behind the scenes: determines the physical host class you're scheduled onto. Production rec: benchmark under real load before committing to a size; don't guess. Cost: instance type is the single biggest line item on your bill — right-sizing matters more than almost anything else here.

3. Key pair

Select: create new or choose existing. Why: needed for SSH access. Behind the scenes: only the public key is stored by AWS; private key is downloaded once and never recoverable. Production rec: use Session Manager (SSM) instead of SSH keys where possible — no key to lose, no port 22 to expose. Security: never commit the .pem file to source control.

4. Network settings

Select: VPC, subnet (public or private), auto-assign public IP, security group rules. Why: determines reachability. Behind the scenes: an ENI is created in the chosen subnet; SG rules are attached to that ENI. Production rec: application instances go in private subnets, reachable only via a load balancer in a public subnet. Security: never open SSH/RDP to 0.0.0.0/0 — restrict to a bastion/VPN CIDR or use SSM. Cost: a NAT Gateway for private-subnet outbound traffic has its own hourly + per-GB cost.

5. Storage

Select: volume type (gp3 default), size, "Delete on Termination" flag, encryption. Why: gp3 gives baseline 3000 IOPS/125MB/s independent of size, cheaper than gp2 at equivalent performance. Behind the scenes: creates an EBS volume in the same AZ as the instance. Production rec: enable encryption by default at the account level (EBS encryption by default setting). Security: unencrypted volumes are a common compliance finding. Cost: oversized, unused volumes are a classic source of silent waste.

6. IAM instance profile & advanced details

Select: attach an IAM role scoped to least privilege, set IMDSv2 to "required", add user-data if bootstrapping. Why: avoids hardcoded credentials and closes the IMDSv1 SSRF risk. Behind the scenes: the role's trust policy already allows ec2.amazonaws.com; STS issues rotating temp credentials to the instance automatically. Production rec: one narrowly-scoped role per application tier, not one shared admin-ish role. Security: this is the single most impactful IAM decision at launch time.

AWS CLI commands

A. Beginner

describe & launch
# List instances in the current region
aws ec2 describe-instances --query "Reservations[].Instances[].[InstanceId,State.Name,InstanceType]" --output table

# Launch a basic instance
aws ec2 run-instances \
  --image-id ami-0abcd1234ef567890 \
  --instance-type t3.micro \
  --key-name my-key \
  --security-group-ids sg-0123456789abcdef0 \
  --subnet-id subnet-0123456789abcdef0 \
  --count 1

# Stop / Start / Terminate
aws ec2 stop-instances --instance-ids i-0123456789abcdef0
aws ec2 start-instances --instance-ids i-0123456789abcdef0
aws ec2 terminate-instances --instance-ids i-0123456789abcdef0   # DESTRUCTIVE

Production use case: describe-instances with a --filters flag is the backbone of most inventory/automation scripts. Common error: UnauthorizedOperation — the IAM identity lacks ec2:RunInstances or related resource-level permissions. Troubleshoot: check the attached policy's Action/Resource/Condition against what you're requesting via aws sts get-caller-identity plus IAM policy simulator.

B. Intermediate

tags, volumes, snapshots
# Tag a resource
aws ec2 create-tags --resources i-0123456789abcdef0 --tags Key=Environment,Value=Production

# Create an EBS snapshot (backup)
aws ec2 create-snapshot --volume-id vol-0123456789abcdef0 --description "pre-patch backup"

# Attach an existing volume
aws ec2 attach-volume --volume-id vol-0123456789abcdef0 --instance-id i-0123456789abcdef0 --device /dev/sdf

# Allocate and associate an Elastic IP
aws ec2 allocate-address --domain vpc
aws ec2 associate-address --instance-id i-0123456789abcdef0 --allocation-id eipalloc-0123456789abcdef0

Production use case: snapshotting before any risky change (patching, migration) is a standard runbook step. Common error: VolumeInUse when attaching a device name already taken — check describe-volumes for existing mappings first.

C. Advanced

launch templates, ASG
# Create a launch template (used by ASGs)
aws ec2 create-launch-template \
  --launch-template-name prod-web-lt \
  --version-description "v1" \
  --launch-template-data file://lt-data.json

# Create an Auto Scaling Group from that template
aws autoscaling create-auto-scaling-group \
  --auto-scaling-group-name prod-web-asg \
  --launch-template LaunchTemplateName=prod-web-lt,Version='$Latest' \
  --min-size 2 --max-size 10 --desired-capacity 2 \
  --vpc-zone-identifier "subnet-aaa,subnet-bbb" \
  --target-group-arns arn:aws:elasticloadbalancing:...:targetgroup/prod-tg/abc123

# Request Spot instances for fault-tolerant workloads
aws ec2 request-spot-instances \
  --instance-count 4 \
  --type "one-time" \
  --launch-specification file://spot-spec.json

Production use case: launch templates + ASG is the standard pattern for any horizontally-scaled web tier. Common error: ASG stuck with 0 healthy instances — usually a bad AMI/user-data script failing health checks, or a target group health check misconfigured.

D. Production

IMDSv2 enforcement, encryption defaults
# Enforce IMDSv2 on an existing instance
aws ec2 modify-instance-metadata-options \
  --instance-id i-0123456789abcdef0 \
  --http-tokens required \
  --http-endpoint enabled

# Enable EBS encryption by default for the account/region
aws ec2 enable-ebs-encryption-by-default

# Rotate: create AMI from a running instance for redeploy
aws ec2 create-image --instance-id i-0123456789abcdef0 --name "golden-ami-2026-08-09" --no-reboot

Production use case: IMDSv2 enforcement across the fleet is a standard hardening pass after any SSRF finding. Common error: forcing IMDSv2 breaks older SDK versions that don't support token-based requests — check SDK versions before a fleet-wide rollout.

E. Troubleshooting

diagnostics
# Check instance status (system + instance level checks)
aws ec2 describe-instance-status --instance-ids i-0123456789abcdef0

# Get console output (useful when SSH is unreachable)
aws ec2 get-console-output --instance-id i-0123456789abcdef0

# Get a screenshot of the boot screen (Windows/stuck boots)
aws ec2 get-console-screenshot --instance-id i-0123456789abcdef0

# Inspect security group rules
aws ec2 describe-security-groups --group-ids sg-0123456789abcdef0

Production use case: describe-instance-status is the first command in almost every "instance unreachable" incident — it separates a hypervisor/host problem (system status) from an OS-level problem (instance status). Common error: status check failure with no console output — often a corrupted filesystem or bad kernel; recovery is via volume detach/mount on a rescue instance.

F. Automation

scripted patch cycle
# Example: cordon, patch, and validate via SSM (no SSH needed)
aws ssm send-command \
  --instance-ids i-0123456789abcdef0 \
  --document-name "AWS-RunPatchBaseline" \
  --parameters '{"Operation":["Install"]}'

aws ssm list-command-invocations --command-id <command-id> --details

Production use case: SSM-driven patch automation removes the need for SSH/bastion entirely for routine maintenance — the standard for large fleets.

Real-world production use cases

1. Horizontally-scaled web tier

Problem: traffic varies 10x between day and night. Architecture: ALB → ASG (private subnets, 2+ AZs) → RDS Multi-AZ. How EC2 solves it: ASG scales the fleet on request count/CPU. Security: instances have no public IP; only ALB is internet-facing. Monitoring: CloudWatch target response time + healthy host count. Scaling: target-tracking policy on ALB request count per target. Failure scenario: one AZ goes down — ASG relaunches lost capacity in remaining AZs. Cost: mix of Reserved (baseline) + Spot (burst) instances.

2. Self-managed batch processing fleet

Problem: nightly data processing job needs 100 cores for 2 hours only. Architecture: Spot Fleet triggered by an EventBridge schedule, pulling jobs from SQS. How EC2 solves it: Spot gives ~70% discount for fully interruption-tolerant work. Security: IAM role scoped to only the specific SQS queue/S3 bucket. Monitoring: queue depth + spot interruption notices. Scaling: fleet size tied to queue backlog. Failure scenario: Spot interruption — job is idempotent and re-queues itself. Cost: this is the textbook Spot use case.

3. Bastion-free administrative access

Problem: engineers need shell access to private-subnet instances without exposing SSH. Architecture: SSM Session Manager, no bastion host, no open port 22. How EC2 solves it: SSM agent (pre-installed on AL2023) connects outbound only. Security: access controlled entirely by IAM policy + optional session logging to S3/CloudWatch. Monitoring: CloudTrail logs every session start. Failure scenario: SSM agent not running — instance becomes unreachable via SSM, need console/EC2 Serial Console as fallback. Cost: free — no bastion instance to run 24/7.

4. Self-hosted CI/CD runners

Problem: hosted CI minutes are expensive at scale; builds need custom tooling. Architecture: ephemeral EC2 runners launched per-job via ASG or Lambda-triggered run-instances, terminated after job completion. Security: short-lived instance role scoped to build artifacts bucket only. Monitoring: build duration + runner launch failures. Failure scenario: runner fails to register — usually a user-data script error; check console output. Cost: Spot for non-critical branches, On-Demand for main/release builds.

5. Licensed legacy software migration

Problem: an ERP system requires per-core licensing tied to physical hardware. Architecture: Dedicated Hosts for full physical isolation and BYOL compliance. Security: stricter network isolation, often in a dedicated VPC. Monitoring: host-level utilization to justify host count. Failure scenario: host hardware failure — requires host replacement and instance migration, planned via maintenance windows. Cost: Dedicated Hosts are the most expensive EC2 purchase option — justified only by licensing/compliance need.

6. Machine learning training

Problem: training a large model needs GPU compute for days at a time. Architecture: p-family/g-family GPU instances in a cluster placement group with EFA networking. Security: training data accessed via VPC endpoint to S3, never public internet. Monitoring: GPU utilization via CloudWatch agent. Failure scenario: checkpointing to S3 regularly so a Spot interruption doesn't lose days of training. Cost: GPU instances are extremely expensive — Spot + checkpointing is the standard cost-control pattern.

7. Multi-region disaster recovery

Problem: a regional AWS outage must not take down the whole business. Architecture: warm-standby ASG in a secondary region, AMIs replicated cross-region, Route 53 failover routing. Security: identical IAM/security posture replicated via IaC in both regions. Monitoring: Route 53 health checks trigger failover. Failure scenario: primary region degraded — DNS fails over, standby ASG scales from minimal to full capacity. Cost: warm standby costs more than backup-only DR but has far better RTO.

8. Compliance-isolated workload

Problem: PCI-DSS workload must be network-isolated from the rest of the environment. Architecture: dedicated VPC/subnet, no internet route, VPC endpoints only, strict SG/NACL pairing. Security: CloudTrail + Config rules enforcing encryption and no public IP. Monitoring: GuardDuty + Config compliance dashboard. Failure scenario: a Config rule flags a non-compliant change — auto-remediation via Lambda reverts it. Cost: compliance tooling overhead is justified by audit requirements.

9. Blue/green deployment

Problem: zero-downtime releases with instant rollback. Architecture: two ASGs (blue/green) behind the same ALB, traffic shifted via target group weighting. Security: identical security posture on both environments by definition (same launch template). Monitoring: error rate comparison between blue and green during shift. Failure scenario: green shows elevated errors — instantly shift weight back to blue. Cost: running two fleets briefly during deploys costs more but de-risks releases.

10. Cost-optimized dev/test environments

Problem: dev instances run 24/7 but are only used 9 hours a day. Architecture: EventBridge-scheduled Lambda stopping/starting instances outside business hours. Security: unaffected — same SGs/IAM apply when running. Monitoring: Cost Explorer tagged by environment to prove savings. Failure scenario: an engineer needs the instance outside hours — self-service Lambda to manually start it. Cost: can cut dev/test EC2 spend by roughly 60-70%.

Hands-on labs

Lab 1 · Beginner

Launch and connect to your first instance

Objective: launch an Amazon Linux instance and SSH into it. Prerequisites: AWS account, default VPC. Steps: create a key pair → launch a t3.micro with SSH (22) open to your IP only → ssh -i key.pem ec2-user@<public-ip> → run uptime. Validation: aws ec2 describe-instance-status --instance-ids <id> shows both checks passed. Common error: connection timeout — usually SG doesn't allow your current IP. Cleanup: aws ec2 terminate-instances --instance-ids <id>. What you learned: the launch → boot → connect flow end to end.

Lab 2 · Basic production

Instance behind a load balancer

Objective: two instances in two AZs behind an ALB serving a simple web page. Steps: launch 2 instances in different AZs, install nginx via user-data → create a target group, register both instances → create an ALB in public subnets. Validation: hit the ALB DNS name repeatedly, confirm responses alternate between instances. Common error: target shows "unhealthy" — check SG allows ALB→instance on the health check port. Cleanup: delete ALB, target group, then terminate instances. What you learned: the fundamental HA web pattern.

Lab 3 · Intermediate

Auto Scaling Group with a launch template

Objective: replace Lab 2's manual instances with a self-healing ASG. Steps: create a launch template referencing your golden AMI → create an ASG (min 2, max 4) attached to the target group from Lab 2 → terminate an instance manually and watch it get replaced. Validation: aws autoscaling describe-auto-scaling-groups shows desired capacity restored within minutes. Common error: new instances fail health checks — check user-data script logs via console output. Cleanup: delete ASG (it terminates its own instances), then the launch template.

Lab 4 · Advanced

Spot Fleet for a batch job

Objective: run a disposable batch job across multiple Spot instance types for resilience. Steps: write a Spot Fleet request spanning 3 instance types across 2 AZs → launch → observe instances process a sample SQS queue → simulate interruption by manually terminating one. Validation: queue backlog still drains despite the interruption. Common error: Spot request stuck "pending-fulfillment" — insufficient capacity for chosen types; widen the type list. Cleanup: cancel the Spot Fleet request, delete the SQS queue.

Lab 5 · Security

Harden an instance: IMDSv2, private subnet, SSM-only access

Objective: remove SSH entirely, enforce IMDSv2, move instance to a private subnet. Steps: launch in a private subnet with an SSM-capable IAM role → connect via aws ssm start-session → run modify-instance-metadata-options --http-tokens required → confirm curl to IMDS without a token now fails. Validation: SSM session succeeds; direct SSH from your machine fails (no route). Common error: SSM session fails — instance role missing AmazonSSMManagedInstanceCore policy. Cleanup: terminate instance.

Lab 6 · Monitoring

CloudWatch alarms and dashboards

Objective: alert when CPU exceeds 80% for 5 minutes. Steps: install the CloudWatch agent for memory/disk metrics (not collected by default) → create an alarm on CPUUtilization → stress-test the CPU with stress-ng → confirm the alarm fires and notifies an SNS topic. Validation: alarm state transitions to ALARM in the console within the evaluation period. Common error: memory alarms never trigger — default EC2 metrics don't include memory; the CloudWatch agent is required. Cleanup: delete alarm, remove agent, terminate instance.

Lab 7 · Automation

Terraform-managed instance + ASG

Objective: recreate Lab 3 entirely as code. Steps: write a Terraform config with aws_launch_template and aws_autoscaling_group resources → terraform plan → terraform apply → modify desired capacity in code and re-apply. Validation: terraform plan shows zero drift after apply. Common error: state drift after a manual console change — always change infrastructure through code once it's under Terraform. Cleanup: terraform destroy.

Lab 8 · Failure simulation

Simulate an AZ failure

Objective: prove your ASG survives an AZ outage. Steps: with an ASG spanning 2 AZs, manually terminate all instances in one AZ simultaneously → watch behavior. Validation: ASG launches replacement capacity in the remaining healthy AZ; ALB stops routing to the dead AZ automatically. Full 3-tier reference build

Security

  • IAM / least privilege: one narrowly scoped role per application tier — never attach AdministratorAccess to an instance profile.
  • Encryption: enable EBS encryption by default at the account level; use KMS customer-managed keys when you need audit control over who can decrypt.
  • Network security: security groups scoped to specific source SGs/CIDRs, never 0.0.0.0/0 for management ports; NACLs as a coarse subnet-level backstop.
  • Public vs private: only load balancers and bastions (if used at all) sit in public subnets; application and data instances stay private.
  • Secrets/credentials: never bake secrets into an AMI or user-data in plaintext — pull them at boot from Secrets Manager or SSM Parameter Store using the instance role.
  • IMDSv2: enforce --http-tokens required fleet-wide to close the SSRF-credential-theft path.
  • Logging: CloudTrail for all EC2 API calls, VPC Flow Logs for network traffic, centralized and access-restricted.
  • Common mistakes: SSH open to the world, unencrypted volumes, shared broad IAM roles, secrets in user-data, never rotating AMIs so patches never actually land.
Insecure

SG inbound rule: 0.0.0.0/0 → port 22, instance role has s3:* on all buckets, IMDSv1 allowed, secrets hardcoded in user-data.

Secure

No inbound SSH at all (SSM only), role scoped to one bucket prefix, IMDSv2 required, secrets pulled from Secrets Manager at boot.

Networking

EC2 networking is governed by VPC constructs: subnets, route tables, gateways, and the two firewall layers.

Client │ ▼ Internet │ ▼ [Internet Gateway] │ ▼ Public Subnet ── [ALB] │ ▼ Route Table (private) ──▶ [NAT Gateway] ──▶ Internet Gateway (outbound only, for patches/updates) │ ▼ Private Subnet ── [EC2 instance in ASG] │ ▼ Security Group (stateful, instance-level) │ ▼ NACL (stateless, subnet-level) ── evaluated on the way in AND out

Traffic flow explained

  • Public-facing traffic hits the Internet Gateway, which routes to the public subnet where the ALB lives.
  • The ALB forwards to instances in private subnets — those instances have no public IP and cannot be reached directly from the internet.
  • Outbound traffic from private instances (patches, API calls to the internet) routes through a NAT Gateway in the public subnet, which has an IGW route.
  • Every packet in and out of an instance's ENI passes through its security group (stateful — only need to allow one direction) and the subnet's NACL (stateless — must explicitly allow both directions).
  • VPC endpoints (Gateway for S3/DynamoDB, Interface for most other services) let private instances reach AWS services without ever routing through the NAT Gateway or public internet at all — cheaper and more secure.

Route TableDetermines where traffic from a subnet is allowed to go
Internet GatewayEnables two-way internet connectivity for public subnets
NAT GatewayEnables one-way (outbound) internet for private subnets

Troubleshooting master guide

"Something is not working. What do I check first?" — work outward from the symptom, in this order:

  1. Identify the exact symptom (timeout? 5xx? can't SSH? high latency?)
  2. Check AWS Service Health Dashboard for regional issues
  3. Check instance configuration (type, AMI, user-data ran successfully)
  4. Check IAM (does the role/caller have the needed permissions?)
  5. Check networking (route tables, IGW/NAT, subnet)
  6. Check security (SG, NACL, IMDS settings)
  7. Check application/system logs
  8. Check CloudWatch metrics for anomalies
  9. Check dependencies (RDS, S3, downstream APIs)
  10. Check recent changes (deploys, IaC applies, manual console edits)
  11. Reproduce the issue in isolation if possible
  12. Apply the smallest fix that addresses the root cause
  13. Validate the fix under real conditions
  14. Document root cause and prevention in a postmortem

Instance unreachable via SSH

SYMPTOM ↓ Connection timed out on port 22
CAUSES ↓ SG doesn't allow your IP · NACL blocking · instance has no public IP/wrong route table · OS firewall blocking · instance actually down
CHECKS ↓ describe-security-groups, describe-instance-status, check route table has IGW route
LOGS ↓ get-console-output for boot-time failures
FIX ↓ add your current IP to SG, or use SSM Session Manager instead
VALIDATE ↓ successful SSH/SSM session
PREVENT ↓ standardize on SSM so SSH connectivity is never a dependency

Instance status check failed (instance-level)

SYMPTOM ↓ Instance running, unreachable, app down
CAUSES ↓ full disk, kernel panic, OOM kill, corrupted filesystem, bad user-data
CHECKS ↓ get-console-output, get-console-screenshot
LOGS ↓ boot log in console output, dmesg if reachable
FIX ↓ reboot; if that fails, detach root volume, attach to a rescue instance, inspect/fix, reattach
VALIDATE ↓ status checks pass, app responds
PREVENT ↓ disk-usage alarms before it fills, memory alarms before OOM

ALB shows all targets unhealthy

SYMPTOM ↓ 502/503 from the load balancer
CAUSES ↓ app not listening on expected port, SG doesn't allow ALB→instance, health check path returns non-200
CHECKS ↓ target group health check settings, ss -tulnp on instance, SG rule for health-check port
LOGS ↓ app logs for the health check path specifically
FIX ↓ correct SG rule or health check path/port
VALIDATE ↓ targets show "healthy" in target group
PREVENT ↓ bake health-check validation into your deploy pipeline

ASG stuck, not launching new instances

SYMPTOM ↓ Desired capacity not reached
CAUSES ↓ hitting a service quota (vCPU limit), bad AMI, insufficient capacity in AZ, launch template error
CHECKS ↓ ASG "Activity History" tab for the exact launch error
LOGS ↓ ASG activity log shows the API error verbatim
FIX ↓ request a quota increase, fix launch template, add more AZs/instance types
VALIDATE ↓ desired = running count
PREVENT ↓ proactively monitor quota usage vs limits

App can't reach S3 / another AWS service

SYMPTOM ↓ AccessDenied or connection errors from the app
CAUSES ↓ missing IAM permission, wrong region endpoint, no route to a VPC endpoint from a private subnet with no NAT
CHECKS ↓ IAM policy simulator, aws sts get-caller-identity from the instance
LOGS ↓ CloudTrail for the exact denied action
FIX ↓ add the missing action/resource to the role's policy, or add a VPC endpoint/NAT route
VALIDATE ↓ app call succeeds
PREVENT ↓ IAM policies generated from Access Analyzer against actual usage, not guessed

Sudden high latency, no error rate change

SYMPTOM ↓ Response times climb, requests still succeed
CAUSES ↓ CPU credit exhaustion (t-family), EBS IOPS throttling, downstream DB slow, GC pauses
CHECKS ↓ CPUCreditBalance, vmstat/iostat, DB metrics
LOGS ↓ app-level slow-query/timing logs
FIX ↓ move off burstable type, provision more IOPS, tune GC or DB
VALIDATE ↓ latency returns to baseline
PREVENT ↓ alarm on CPU credit balance trending toward zero, not just CPU%

Costs spiked overnight

SYMPTOM ↓ Unexpected billing jump
CAUSES ↓ runaway ASG scaling, orphaned EIPs, forgotten large instances, data transfer spike, Spot fallback to On-Demand pricing
CHECKS ↓ Cost Explorer filtered by service/tag, ASG activity history
LOGS ↓ CloudTrail for who launched what and when
FIX ↓ cap ASG max size, release unused EIPs, add budget alarms
VALIDATE ↓ daily spend returns to baseline
PREVENT ↓ AWS Budgets with alert thresholds, mandatory tagging for attribution

Instance disappeared / can't find it

SYMPTOM ↓ Instance ID no longer in describe-instances
CAUSES ↓ Spot interruption/reclaim, ASG scale-in terminated it, someone manually terminated it, lifecycle hook auto-terminated
CHECKS ↓ CloudTrail for TerminateInstances events, ASG activity history, Spot interruption notices
LOGS ↓ CloudTrail event history with the exact caller identity
FIX ↓ relaunch from ASG/template if it was meant to be persistent
VALIDATE ↓ replacement is healthy and serving traffic
PREVENT ↓ termination protection for genuinely stateful, irreplaceable instances

Incident scenarios (act as production support)

"Application suddenly stopped working."

Step 1 — confirm scope: one instance or the whole fleet? Step 2 — check ALB target health; if all unhealthy, it's likely a shared cause (bad deploy, dependency down) not per-instance. Step 3 — check recent deploys/changes via CloudTrail. Step 4 — check app logs for the exact exception. Why each step: scope-first prevents chasing a single-instance issue when it's actually a fleet-wide deploy regression.

"Users are receiving timeout errors."

Step 1 — differentiate connection timeout (network/SG) vs response timeout (app slow). Step 2 — check SG/NACL if connection-level. Step 3 — check CPU/DB latency if response-level. Step 4 — check ALB idle timeout setting vs app response time. Why: the fix is completely different depending on which timeout type it is — network vs app performance.

"Permission denied."

Step 1 — identify exactly which action failed from the error message/logs. Step 2 — check if it's an IAM issue (AWS API call) or a Linux filesystem permission issue. Step 3 — for IAM, use the policy simulator against the exact action+resource. Step 4 — for filesystem, check ls -l ownership. Why: "permission denied" is ambiguous until you know which layer it's coming from.

"Service running but users can't connect."

Step 1 — confirm app is actually listening (ss -tulnp). Step 2 — check SG allows the port from the client's source. Step 3 — check NACL isn't silently dropping return traffic. Step 4 — check route table has a path to the client. Why: "running" only proves the process exists — reachability is a separate, multi-layer question.

"Deployment failed."

Step 1 — check the deploy tool's own error output first. Step 2 — if it's a new AMI/launch template, check ASG activity history for the launch error. Step 3 — check user-data script exit codes via console output. Step 4 — roll back to the last known-good launch template version. Why: launch template versioning makes rollback a one-line change instead of a manual rebuild.

Cost optimization

  • What causes cost: instance hours (by type), EBS storage + provisioned IOPS, data transfer (especially cross-AZ and to internet), Elastic IPs left unattached, snapshots retained indefinitely.
  • Free tier: 750 hours/month of t2.micro/t3.micro for 12 months on new accounts — check current terms, as free tier offers change.
  • Common expensive mistakes: oversized instances "just in case", forgotten dev/test instances left running, unattached EIPs, orphaned snapshots from terminated instances, On-Demand pricing for steady-state workloads that should be Reserved.
  • Optimization techniques: right-size using actual CloudWatch utilization data (not guesses); Reserved Instances or Savings Plans for predictable baseline load; Spot for fault-tolerant/batch workloads; scheduled stop/start for dev/test; gp3 instead of gp2 (cheaper at equal performance); lifecycle policies to expire old snapshots.
  • Tools: Cost Explorer for trend analysis and RI/Savings Plan recommendations, AWS Budgets for proactive alerting, Compute Optimizer for right-sizing recommendations based on real usage.
Realistic example

A team running 10 m5.2xlarge instances 24/7 for a workload that's actually 20% utilized on average could cut cost by roughly half just by right-sizing to m5.large plus a Savings Plan — without any architecture change.

L1: (1) Amazon Machine Image — a bootable template with OS + optional pre-installed software. (2) Stop preserves the EBS root volume and instance ID, billing pauses for compute; terminate destroys the instance permanently (and instance-store data). (3) Yes, EBS is independent of the instance lifecycle unless "delete on termination" is set. (4) A stateful, instance-level virtual firewall. (5) To securely SSH into a Linux instance without a password.

L2: (1) SG is stateful/instance-level/allow-only; NACL is stateless/subnet-level/allow+deny. (2) A wrapper around an IAM role attached to the instance so apps get auto-rotating temporary credentials instead of static keys. (3) Instance-store data is lost on both stop and terminate (and any underlying hardware failure) — it only survives a reboot. (4) A reusable, versioned instance configuration template used by ASGs and repeatable launches. (5) It exhausted its CPU credit balance — burstable instances throttle once credits run out.

L3: (1) Cluster = same rack for low latency; spread = max 7 per rack for fault isolation; partition = grouped racks for distributed systems needing both. (2) IMDSv2 requires a session token obtained via a PUT request, which most naive SSRF vectors (that only do GET) can't replicate. (3) Spot can be reclaimed with 2-minute notice — unsuitable for stateful services unless the state is externalized/replicated elsewhere. (4) By default, oldest launch configuration/most instances in the AZ with the most capacity, but this is configurable via termination policies. (5) gp3 has baseline performance decoupled from size and is cheaper; io2 offers higher, more consistent IOPS for latency-sensitive databases.

L4: (1) Rolling ASG Instance Refresh with a minimum healthy percentage, driven by a new launch template version from a patched golden AMI. (2) Never put secrets in user-data plaintext — pull them from Secrets Manager/Parameter Store at boot using the instance role. (3) Reserved/Savings Plan for the always-on baseline, Spot for elastic/fault-tolerant burst, On-Demand only as a fallback when Spot capacity is unavailable. (4) Enable EBS encryption by default account-wide and add an AWS Config rule denying unencrypted volume creation. (5) Scheduled rebuilds via EC2 Image Builder pipeline, old AMI versions deprecated and eventually deregistered with their snapshots cleaned up.

L5: (1) Target group health check configuration and the SG rule allowing the ALB to reach the health check port. (2) Check SG rules for your IP, then NACL, then whether the instance actually has a public IP/correct route — narrow layer by layer. (3) Check ASG activity history for the specific launch failure (quota, capacity, bad AMI) — desired capacity alone doesn't tell you why it's not being met. (4) Memory isn't a default EC2 metric — it requires the CloudWatch agent installed and configured. Strong answer: EBS is network-attached, persistent, AZ-locked, independent lifecycle from the instance; instance store is physically attached local disk, ephemeral, lost on stop/terminate/hardware failure, but higher raw IOPS. Weak answer: "EBS is persistent, instance store isn't" with no explanation of why or when to use each. Follow-up: "When would you actually choose instance store in production?"

I3How does Auto Scaling decide when to add or remove instances?▸
Tests: ASG mechanics

Strong answer: scaling policies (target tracking, step, simple) evaluate CloudWatch metrics against thresholds, with cooldown periods to prevent flapping; describes target-tracking as the most common production pattern. Weak answer: "it scales based on CPU" with no mention of policy types or cooldowns. Follow-up: "Your ASG is flapping — what would you change?"

I4What's the shared responsibility model as it applies to EC2?▸
Tests: security ownership boundaries

Strong answer: AWS secures the physical infrastructure, hypervisor, and host; you're responsible for the guest OS, patching, application security, network configuration (SGs/NACLs), and IAM. Weak answer: "AWS handles security" without distinguishing layers. Follow-up: "Who's responsible for OS-level CVE patching?"

I5How would you achieve zero-downtime deployment on EC2?▸
Tests: deployment strategy

Strong answer: rolling ASG Instance Refresh with a minimum healthy percentage, or blue/green with two ASGs and weighted target groups behind one ALB. Weak answer: "just deploy and restart the app" — implies downtime. Follow-up: "How do you roll back mid-deployment if error rates spike?"

Advanced

A1Design a highly available, cost-optimized EC2 architecture for a web application with unpredictable traffic.▸
Tests: end-to-end architecture skill

Strong answer: ALB across ≥2 AZs → ASG with target-tracking scaling, mixed instance policy (Reserved baseline + Spot burst), private subnets, golden AMI + launch template versioning, CloudWatch alarms, RDS Multi-AZ backend. Weak answer: a single large instance "sized for peak." Follow-up: "How do you handle Spot interruptions gracefully mid-request?"

A2How would you prevent SSRF attacks from exfiltrating an instance's IAM credentials?▸
Tests: deep security knowledge, real incident awareness

Strong answer: enforce IMDSv2 (token-required) fleet-wide, since it requires a PUT request most SSRF vectors can't replicate; references the Capital One breach as the canonical case study. Weak answer: "use a firewall" with no mention of IMDSv2 specifically. Follow-up: "What would break if you enforced this fleet-wide today?"

A3Explain placement groups and when each strategy is appropriate.▸
Tests: low-level infra knowledge

Strong answer: cluster for HPC/tightly-coupled low-latency workloads (same rack, single point of failure risk); spread for small numbers of critical instances needing hardware isolation; partition for large distributed systems (Cassandra, Kafka, HDFS) needing both scale and rack-awareness. Weak answer: can name the three but not when to use each. Follow-up: "What's the failure blast radius difference between cluster and spread?"

Scenario-based (STAR-style)

S1"Tell me about a time you diagnosed a production EC2 performance issue."▸
Tests: real troubleshooting experience

Strong answer (STAR): Situation — latency spiked on a t3-family fleet during a traffic surge. Task — restore performance without overspending. Action — checked CPUCreditBalance, found it near zero, moved the fleet to m6i and added target-tracking scaling. Result — latency returned to baseline and stayed stable through the next surge. Weak answer: vague "we looked at the logs and fixed it" with no specific metric or root cause. Follow-up: "How did you prevent recurrence?"

Troubleshooting

T1An ASG keeps launching and immediately terminating instances. Walk me through your diagnosis.▸
Tests: methodical debugging

Strong answer: check ASG activity history for the termination reason first (often failed health checks); check target group health check config vs the app's actual port/path; check console output/user-data logs for a boot-time script failure. Weak answer: jumps straight to "restart everything." Follow-up: "What if console output shows the instance booted fine but still gets terminated?" (Likely a health check misconfiguration, not a boot failure.)

Production

P1How do you patch 500 production EC2 instances without downtime or manual SSH?▸
Tests: fleet-scale operational maturity

Strong answer: SSM Patch Manager with a defined maintenance window, or a golden-AMI rebuild pipeline paired with rolling ASG Instance Refresh — no SSH required either way. Weak answer: "SSH into each one and run yum update." Follow-up: "How do you handle instances that fail to patch?"

Interview rapid fire

What is EC2?
On-demand virtual server compute in AWS.
Why EC2 over Lambda?
Long-running, stateful, or full-OS-control workloads.
When would you NOT use EC2?
Short bursty tasks better suited to Lambda; fully managed needs.
EC2 vs Lambda?
Server you manage vs fully managed, event-driven, no server.
How do you troubleshoot an unreachable instance?
Status checks → console output → SG/NACL → route table.
What happens internally on launch?
Control plane validates → placement engine schedules → Nitro boots VM → ENI/EBS attached.
Production best practice for SSH?
Don't — use SSM Session Manager instead.
What is a launch template?
Versioned, reusable instance launch configuration.
gp3 vs gp2?
gp3 has baseline performance independent of size, cheaper.
What is IMDSv2 for?
Token-required metadata access, blocks basic SSRF credential theft.
Spot vs On-Demand?
Spot is cheaper but reclaimable with 2-min notice; On-Demand is guaranteed.
What's an instance profile?
Wrapper attaching an IAM role to an EC2 instance.
SG vs NACL?
SG stateful/instance-level; NACL stateless/subnet-level.
What causes CPU credit exhaustion?
Sustained load on a burstable (t-family) instance.
How do you patch instances at scale?
SSM Patch Manager or golden AMI + rolling refresh.
What's a placement group?
Controls physical proximity of instances for latency or fault isolation.
Why avoid public IPs on app instances?
Reduces attack surface — access only via load balancer.
What's Auto Scaling's role?
Maintains desired capacity automatically based on metrics.
Where do memory metrics come from?
CloudWatch agent — not a default metric.
What's a Dedicated Host for?
Physical isolation for compliance/licensing needs.
Root volume encryption default?
Off unless you enable EBS encryption by default at the account level.
What's user-data used for?
Bootstrap script executed by cloud-init on first boot.
How is EC2 billed?
Per-second, by instance type/size, plus storage and data transfer.
What's a Reserved Instance?
Committed-use discount for predictable, steady-state workloads.
Multi-AZ vs Multi-region?
AZ protects against a datacenter failure; region against a regional outage.
What does a status check failure mean?
System = host/hardware issue; Instance = OS-level issue.
How do you avoid hardcoded credentials?
Attach an IAM role via instance profile; use IMDS-issued temp creds.
What's ENA?
Enhanced networking driver for higher throughput/lower latency.
Blue/green vs rolling deploy?
Blue/green swaps entire environments; rolling replaces incrementally.
What's the first troubleshooting step, always?
Identify and scope the exact symptom before touching anything.

Production checklist

  • Security: No SG open to 0.0.0.0/0 on mgmt ports
  • IAM: Least-privilege instance profile per tier
  • Networking: App instances in private subnets
  • Encryption: EBS encryption enabled by default
  • Monitoring: CloudWatch agent + custom metrics installed
  • Logging: CloudTrail + VPC Flow Logs centralized
  • Backup: Snapshot lifecycle policy configured
  • Scaling: ASG with target-tracking policy
  • Availability: ≥2 AZs, min capacity ≥2
  • DR: Cross-region AMI copy and tested restore
  • Cost: Right-sized, RI/Savings Plan baseline in place
  • Automation: Infrastructure defined and applied via IaC
  • Access: SSM Session Manager, no standing SSH
  • Patching: Scheduled via SSM Patch Manager or AMI pipeline
  • Alarms: CPU, memory, disk, status checks all alarmed
  • Documentation: Runbooks for common incidents exist
  • Tagging: Consistent tags for cost/ownership attribution
  • Termination protection: Enabled for genuinely stateful instances
