Version Control · Git & GitHub

Git tracks your code.
GitHub is where your team meets it.

Git is a distributed version control system that runs entirely on your machine. GitHub is a hosted service built around Git that adds collaboration, review, automation, and a hub for every other tool in your pipeline to plug into. This guide covers both — from the internals that make Git actually make sense, through production branching strategy, to the interview questions that separate "I use git commit and git push" from real understanding.

01

Git vs GitHub — the distinction that matters

Git is a distributed version control system, created by Linus Torvalds in 2005 to manage the Linux kernel's source history. It runs locally — every clone of a repository is a full copy of the entire history, with no dependency on a central server to function. You can commit, branch, merge, and view history entirely offline.

GitHub is a company/platform (owned by Microsoft since 2018) that hosts Git repositories in the cloud and wraps them with collaboration tooling: pull requests, code review, issue tracking, CI/CD (Actions), package registries, security scanning, and project management. GitHub didn't invent Git — it's the most popular place to host Git repositories and collaborate around them. GitLab and Bitbucket are direct competitors offering similar hosting-plus-collaboration layers.

Why Git was created

Centralized version control systems (like SVN, CVS) required constant network access and had a single point of failure — the central server. Distributed version control solved this: every developer has the complete history locally, commits are fast (no network round-trip), and branching/merging is cheap enough to use constantly instead of avoiding it.

Why GitHub matters on top of Git

Git alone has no concept of "pull request," "issue," or "who's allowed to merge to main." GitHub adds the social/organizational layer — review workflows, permissions, automation triggers — that turns a version control tool into a team collaboration platform.

When NOT to reach for GitHub specifically

  • Highly regulated/air-gapped environments — self-hosted GitLab or Gitea inside your own network instead of a public SaaS platform.
  • Existing GitLab-centric CI/CD investment — migrating just for GitHub-specific features rarely justifies the cost.
  • You need on-prem hosting with GitHub's UI — GitHub Enterprise Server exists for this, but it's a different product from github.com.
02

Git architecture — the three trees

Nearly every Git command moves changes between three areas. Understanding this model makes every command's behavior predictable instead of memorized.

Working Directory Staging Area (Index) Repository (.git) (your files) (git add) (git commit) │ │ │ │──── git add ────────────▶│ │ │ │──── git commit ───────────▶│ │◀─── git checkout ────────┼────────────────────────────│ │◀────────────────────── git reset ──────────────────────│ Local Repository Remote Repository (GitHub) │ │ │──────────── git push ───────────────▶│ │◀─────────── git pull / fetch ─────────│

Step-by-step

  • Working directory: the actual files on disk you're editing — Git compares these against the last commit to determine what's "changed."
  • Staging area (index): a snapshot-in-progress — git add moves specific changes here, letting you build a commit out of only some of your edits, not necessarily everything you've touched.
  • Local repository: git commit takes what's staged and permanently records it as a new snapshot in your local .git history — this step requires no network access at all.
  • Remote repository: git push/git pull sync your local history with a remote copy (GitHub) — this is the only step that touches the network.
What an interviewer expects you to know

That committing is a local, offline operation, and pushing is a separate, explicit, network operation — a huge number of "my changes disappeared" incidents trace back to someone not realizing they committed locally but never pushed.

03

Core concepts

1. Commit

Simple: a saved snapshot of your project at a point in time, with a message describing the change. Technical: an immutable object containing a pointer to a tree (the file/directory snapshot), a pointer to its parent commit(s), author/committer metadata, and a message — identified by a SHA-1 (or SHA-256 in newer configs) hash of all of that content. Why it exists: to create an auditable, addressable history where every state of the project can be referenced and restored. Use case: reverting a bad change, understanding when a bug was introduced via git blame/bisect. Common mistake: giant commits mixing unrelated changes, making history useless for review or bisecting. Interview Q: "What makes a commit hash change?" → any change to its content, parent, or metadata — which is why commits are effectively tamper-evident.

2. Branch

Simple: a movable pointer to a specific commit, letting you work on changes in isolation. Technical: literally a 41-byte file containing a commit SHA, stored under .git/refs/heads/ — this is why branching in Git is nearly instantaneous, unlike systems that copy the whole codebase per branch. Why it exists: to let multiple lines of work (features, fixes, experiments) progress independently without interfering with each other. Use case: a feature branch off main, developed and reviewed independently before merging. Common mistake: long-lived branches that drift so far from main that merging becomes a painful, conflict-heavy event. Interview Q: "Why is branching in Git so cheap compared to older VCS tools?" → because a branch is just a pointer, not a full copy of the codebase.

3. HEAD

Simple: a pointer to "where you currently are" — usually the tip of your current branch. Technical: a reference (in .git/HEAD) that normally points to a branch ref, which in turn points to a commit; when it points directly to a commit instead of a branch, you're in "detached HEAD" state. Why it exists: Git needs to know what your next commit's parent will be, and what git checkout/git switch are relative to. Use case: HEAD~1, HEAD^ are common shorthand for "one commit back from where I am now." Common mistake: committing in detached HEAD state and then switching branches, seemingly "losing" the commits (they're still there, just unreferenced — recoverable via reflog). Interview Q: "How do you recover commits made in a detached HEAD state?" → git reflog to find the commit SHA, then create a branch pointing at it.

4. Merge

Simple: combining changes from one branch into another. Technical: either a fast-forward (if the target branch has no divergent commits, the pointer simply moves forward) or a three-way merge (creates a new "merge commit" with two parents, using the common ancestor to compute the combined diff). Why it exists: to bring independently developed work back together into a shared history. Use case: merging a reviewed pull request into main. Common mistake: merging without pulling the latest target branch first, causing avoidable conflicts. Interview Q: "What's a fast-forward merge?" → when the target branch hasn't diverged, so Git just moves the pointer forward with no new merge commit needed.

5. Remote

Simple: a reference to a hosted copy of the repository, usually named origin. Technical: a named URL entry in .git/config that git fetch/push/pull operate against; a repo can have multiple remotes (e.g. origin and upstream for a fork). Why it exists: to let distributed local repositories synchronize with each other through a shared hosted point. Use case: upstream remote for pulling updates from the original repo you forked. Common mistake: pushing to the wrong remote, especially after forking, sending changes somewhere unintended. Interview Q: "What's the difference between origin and upstream?" → origin is your own remote (often your fork); upstream is the original repo you forked from.

6. Tag

Simple: a fixed, named pointer to a specific commit, typically used for releases. Technical: unlike a branch, a tag doesn't move as new commits are added — annotated tags are full Git objects with their own metadata (tagger, message, optionally GPG-signed); lightweight tags are just a named pointer. Why it exists: to mark meaningful, permanent points in history (releases, milestones) separately from the constantly-moving branch pointers. Use case: v2.3.0 tagged on the exact commit that was deployed to production. Common mistake: using lightweight tags for releases when annotated tags (with signing) are the production-appropriate choice. Interview Q: "Why use an annotated tag instead of lightweight for a release?" → it carries metadata and can be GPG-signed for provenance verification.

04

Git internals — what's actually in .git

Git's entire data model is four object types, all content-addressed by SHA hash, stored in .git/objects.

ObjectContainsAnalogy
BlobRaw file content (no filename, no metadata)A file's contents, nameless
TreeA directory listing — filenames + modes + pointers to blobs/treesA folder structure
CommitPointer to a tree, parent commit(s), author, messageA labeled snapshot in time
Tag (annotated)Pointer to a commit, plus tagger metadataA permanent bookmark

Why content-addressing matters: a blob's hash is derived purely from its content — so two identical files anywhere in history, even in unrelated commits, are stored once. This is also why Git can efficiently detect that "this content already exists" without comparing bytes manually.

peek inside .git
# See what a commit object actually contains
git cat-file -p HEAD

# See the tree a commit points to
git cat-file -p HEAD^{tree}

# See the raw type of any object
git cat-file -t <sha>
What an interviewer expects

That you understand a commit doesn't store a "diff" — it stores a full snapshot (tree) at that point, and Git computes diffs on the fly by comparing trees. This is a common misconception worth correcting explicitly in an interview answer.

05

Core commands

Everyday basics

git init                          # create a new repo
git clone <url>                   # copy a remote repo locally, with full history
git status                        # see what's changed/staged
git add <file>                    # stage specific changes
git commit -m "message"          # save a snapshot of staged changes
git log --oneline --graph         # view history compactly
git diff                          # unstaged changes vs last commit
git diff --staged                 # staged changes vs last commit

Branching & remotes

git branch feature-x               # create a branch
git switch feature-x                # move to it (modern replacement for checkout)
git switch -c feature-x             # create + switch in one step
git push -u origin feature-x        # push and set upstream tracking
git fetch origin                    # download remote changes, don't merge yet
git pull                            # fetch + merge (or rebase, if configured) in one step

Undoing things (know the difference)

git restore <file>                  # discard uncommitted changes to a file
git restore --staged <file>         # unstage, keep the edits
git reset --soft HEAD~1             # undo last commit, keep changes staged
git reset --mixed HEAD~1            # undo last commit, keep changes unstaged (default)
git reset --hard HEAD~1             # undo last commit, DISCARD the changes entirely
git revert <sha>                    # create a NEW commit that undoes a prior one (safe for shared history)
git reflog                          # recovery lifeline — shows every HEAD movement, even after reset
Critical distinction

git reset rewrites history and is fine on branches only you use. git revert adds a new commit undoing an old one, preserving history — this is the only safe option once a commit has been pushed and others may have based work on it.

Stash & cherry-pick

git stash                           # shelve uncommitted changes temporarily
git stash pop                       # reapply and remove the stashed changes
git cherry-pick <sha>               # apply one specific commit onto the current branch

Production use case: cherry-pick is the standard way to backport a single bugfix commit to a release branch without merging the entire feature branch it originated on.

06

Branching & merging in practice

main: A───B───C─────────────F───G \ / feature: D───E────────╯ (merge commit F)

A feature branch diverges from main at commit C, develops independently through D and E, and rejoins via a merge commit F that has two parents — C's line and E. Git then continues normal linear history from there.

Resolving a merge conflict

<<<<<<< HEAD
current branch's version of this line
=======
incoming branch's version of this line
>>>>>>> feature-branch

Edit the file to the correct final content (removing the conflict markers), then git add <file> and continue the merge/rebase. Common mistake: resolving a conflict but forgetting to git add the resolved file before committing/continuing, leaving Git thinking the conflict is still unresolved.

07

Merge vs rebase — the interview classic

MERGE — preserves exact history, adds a merge commit main: A───B───C───────F \ / feature: D────E REBASE — replays your commits on top, linear history, no merge commit main: A───B───C feature: D'───E' (D and E rewritten with new SHAs)
MergeRebase
HistoryPreserves exact chronological history, including a merge commitRewrites commits onto a new base — linear, but the commit SHAs change
Safety on shared branchesAlways safeNever rebase commits that others have already pulled — it rewrites SHAs and breaks their history
Resulting logBranchy, shows exactly what happenedClean and linear, easier to read/bisect
Typical useMerging a finished, reviewed PR into mainCleaning up your own feature branch before opening a PR
The golden rule

Never rebase a branch that other people have already pulled from and built work on top of. Rebase freely on your own local, unshared branches; merge (or squash-merge) for anything that's already shared.

09

GitHub-specific features

Pull Requests

The review-and-merge unit — a proposed set of commits, diffable, commentable, with required-checks and required-approvals gates before merge.

Branch protection rules

Enforce required reviews, required status checks (CI must pass), no force-push, no direct pushes to main — the mechanism that actually makes a branching strategy enforced rather than just documented.

CODEOWNERS

A file mapping paths to required reviewers — automatically requests review from the right team when a PR touches their code.

Issues & Projects

Lightweight tracking linked directly to commits/PRs via keywords like Fixes #123, auto-closing issues on merge.

GitHub Actions

Native CI/CD — YAML-defined workflows triggered by repo events (push, PR, schedule, release) running in hosted or self-hosted runners.

Packages / Container Registry

Hosts npm/Docker/Maven/NuGet packages directly alongside the code that produces them, with the same permission model.

Dependabot

Automated dependency update PRs plus vulnerability alerts scanning your dependency manifests against known CVEs.

Secret scanning / code scanning

Detects committed credentials and, via CodeQL, static analysis vulnerabilities — can block a push containing a detected secret before it ever lands.

10

How GitHub interconnects with everything else

GitHub sits at the center of most DevOps toolchains — not because it does everything, but because its webhook/event system lets every other tool react to what happens in the repo.

CI/CD (Jenkins / CircleCI / GitLab-style runners)

External CI systems subscribe to GitHub webhooks (push, PR opened) to trigger builds; GitHub reports commit statuses back so PR checks show pass/fail directly in the review UI, gating merges via branch protection.

GitHub Actions → cloud deploy

A workflow builds a container, pushes to ECR/GCR/Docker Hub, then calls the cloud provider's deploy API (e.g. updates an ECS service or EKS manifest) — OIDC federation (see the IAM guide) avoids storing static cloud credentials as repo secrets.

Docker / container registries

A Dockerfile in the repo is built by Actions/CI on every merge, tagged with the commit SHA for full traceability from a running container back to the exact commit that produced it.

Kubernetes / Argo CD (GitOps)

In a GitOps model, a separate manifests repo is the source of truth for cluster state — Argo CD/Flux watches that repo and reconciles the live cluster to match it automatically on every merge, no direct kubectl apply needed.

Terraform / IaC

Infrastructure changes go through the same PR review flow as application code — a terraform plan output posted as a PR comment by CI lets reviewers see the exact infra diff before apply runs on merge.

Slack / Teams / PagerDuty

GitHub webhooks notify chat channels on PR events, deploy status, or failed workflows; incident tools can auto-link a triggering deploy's commit SHA into an incident timeline.

Jira / issue trackers

Commit messages/PR titles referencing a ticket ID (e.g. PROJ-123) auto-link and can auto-transition ticket status via integration apps, keeping code state and project tracking in sync.

SSO / IAM

GitHub Enterprise integrates with SAML/OIDC identity providers for org membership and access — repo permissions can map to identity-provider groups rather than being managed manually per user.

GitHub Actions — CI/CD walkthrough

.github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm test

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      id-token: write   # enables OIDC — no static AWS keys stored as secrets
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::111122223333:role/gh-actions-deploy
          aws-region: us-east-1
      - run: ./deploy.sh

Why this is the production pattern: tests gate deploy via needs: test; deploy only runs on main, not every PR; and OIDC federation (Section 10's IAM connection) means there's no long-lived AWS access key sitting in GitHub Secrets waiting to be leaked.

13

Security

  • SSH keys vs HTTPS+token: SSH key pairs or a fine-grained personal access token — never a password, which GitHub no longer accepts for Git operations over HTTPS.
  • GPG/SSH commit signing: proves a commit genuinely came from the claimed author, shown as "Verified" in GitHub's UI — important for supply-chain integrity, especially combined with required signing in branch protection.
  • Secret scanning: GitHub scans pushed content for known credential patterns (AWS keys, API tokens) and can be configured to block the push entirely (push protection) rather than just alert after the fact.
  • Dependabot alerts: flags dependencies with known CVEs, opens automated update PRs — a baseline supply-chain hygiene practice.
  • Least-privilege repo/org permissions: Read/Triage/Write/Maintain/Admin roles, scoped per-repo or per-team, not blanket org-admin for convenience.
  • Fine-grained PATs and short-lived tokens: scope tokens to specific repos and specific permissions instead of classic all-access tokens.
  • Common mistakes: committing .env files with real credentials, using long-lived cloud access keys as Action secrets instead of OIDC, disabling branch protection "temporarily" and forgetting to re-enable it.
Insecure

AWS access key/secret pasted directly into GitHub Secrets, no rotation, direct push access to main for all contributors, no secret scanning.

Secure

OIDC-federated deploy role (no static keys), branch protection with required review + status checks, secret scanning with push protection enabled.

Troubleshooting

"I committed to the wrong branch."

FIX ↓ git log to find the commit SHA · switch to the correct branch · git cherry-pick <sha> · switch back to the wrong branch and git reset --hard HEAD~1 to remove it there
PREVENT ↓ always check git branch/git status before committing

"I force-pushed and now teammates' branches are broken."

CAUSE ↓ a rebase or history rewrite was force-pushed to a shared branch after others had already pulled it
FIX ↓ teammates need git pull --rebase or, in the worst case, to reset their local branch to match the new remote history
PREVENT ↓ use --force-with-lease instead of --force (fails safely if the remote has commits you don't have locally), and never rebase branches others are actively working from

"I need to undo a commit that's already been pushed."

FIX ↓ git revert <sha> — creates a new commit undoing the change, safe for shared history; never reset --hard + force-push on a shared branch
PREVENT ↓ reserve reset for local, unpushed commits only

"My PR shows way more changes than I actually made."

CAUSE ↓ feature branch is out of date with main, so the diff includes everyone else's merged changes too
FIX ↓ git fetch origin && git rebase origin/main (or merge, if the branch is already shared) to bring the branch up to date
PREVENT ↓ rebase/merge from main regularly on long-lived feature branches instead of once at the end

"Merge conflict I don't understand how to resolve."

CHECKS ↓ git status to see conflicted files · open each and look for <<<<<<< markers · use git log --merge to see the commits from both sides
FIX ↓ manually reconcile the content, remove markers, git add, then continue (git rebase --continue or finish the merge commit)
ESCAPE HATCH ↓ git merge --abort or git rebase --abort to cleanly back out if it gets too tangled and start over

16

Interview questions

Fundamentals

Q1What's the difference between Git and GitHub?Easy▸

Git is the distributed version control system itself — it runs locally and needs no server to function. GitHub is a hosted platform built around Git that adds collaboration features: pull requests, code review, issue tracking, CI/CD, and access control.

Q2What's the difference between git fetch and git pull?Easy▸

fetch downloads remote changes into your local repo's remote-tracking branches without touching your working branch. pull is fetch plus an automatic merge (or rebase, if configured) into your current branch. fetch is the safer choice when you want to review incoming changes before integrating them.

Q3What does git reset --hard actually do, and why is it dangerous?Medium▸

It moves the branch pointer to a specified commit and overwrites both the staging area and working directory to match — any uncommitted changes and any commits after that point are discarded from the working tree (though unpushed commits are usually still recoverable briefly via git reflog). It's dangerous because it silently destroys uncommitted work with no confirmation prompt.

Intermediate

I1Explain merge vs rebase, and when you'd use each.Medium▸

Merge combines two branches with a merge commit, preserving exact chronological history — always safe, even on shared branches. Rebase replays your commits onto a new base, producing a linear history but rewriting commit SHAs — safe only on branches nobody else has pulled from. Use merge for integrating a finished, reviewed PR; use rebase to clean up your own branch before opening one.

I2How would you recover a commit after an accidental git reset --hard?Medium▸

git reflog shows every position HEAD has recently pointed to, including the commit that existed before the reset — find its SHA and run git reset --hard <sha> (or git cherry-pick it onto your current branch) to recover it. Reflog entries eventually expire (default ~90 days), so this isn't a permanent safety net.

I3What's the purpose of a .gitignore file, and what happens if you add a pattern for a file that's already tracked?Medium▸

.gitignore tells Git which untracked files to never stage automatically. If a file is already tracked, adding it to .gitignore has no retroactive effect — you need git rm --cached <file> to stop tracking it going forward while leaving it on disk.

Advanced

A1Walk through what happens internally when you run git commit.Hard▸

Git writes a blob object for each changed file's content (if that exact content doesn't already exist as an object), builds tree objects representing the directory structure pointing to those blobs, creates a commit object pointing to the root tree plus the current HEAD as its parent, then moves the current branch ref to point at the new commit — all identified by SHA hashes of their content.

A2How would you design a Git branching + CI/CD strategy for a team doing continuous deployment?Hard▸

GitHub Flow: a single always-deployable main, short-lived feature branches opened as PRs, branch protection requiring passing CI and at least one review before merge, squash-merge for a clean linear history, and an Actions workflow that deploys automatically on every merge to main — feature flags for anything not ready to be fully live, rather than long-lived feature branches.

A3How does GitHub Actions avoid storing long-lived cloud credentials as secrets?Hard▸

Via OIDC federation — the workflow requests a short-lived OIDC token from GitHub's identity provider, which the cloud provider's IAM trusts (scoped to a specific repo/branch via trust policy conditions), and exchanges for temporary credentials through something like AWS STS. No static access key ever needs to be stored in GitHub Secrets at all.

Troubleshooting

T1A teammate says their branch is "completely broken" after you force-pushed to a shared branch — what happened and how do you fix it?Hard▸

The force push rewrote the shared branch's history, so their local branch (based on the old history) now diverges incompatibly from the remote. They need to reconcile — typically git fetch then resetting their local branch to match the new remote history (losing any local-only work first if needed, or rebasing it onto the new base). Going forward, use --force-with-lease and avoid rewriting history on genuinely shared branches.

Cheat sheet

Daily flow

git switch -c feature-x → edit → git add -p → git commit -m "..." → git push -u origin feature-x → open PR → address review → squash-merge

Undo table

Uncommitted, unwanted → git restore <file> · Staged, want to unstage → git restore --staged <file> · Local commit, not pushed → git reset --soft HEAD~1 · Already pushed, shared → git revert <sha>

Recovery lifeline

git reflog → find the SHA before things went wrong → git reset --hard <sha> or git cherry-pick <sha>

Inspect internals

git cat-file -p <sha> · git log --oneline --graph --all · git show <sha> · git blame <file>

Golden rules

Never rebase shared history · always --force-with-lease, never bare --force · revert for shared history, reset only for local · commit early, commit often, push regularly
