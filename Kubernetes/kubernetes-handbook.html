Beginner · 01

Introduction

Kubernetes (often shortened to K8s) is an open-source system for running containers reliably at scale. You describe the state you want — "I want 3 copies of this web server, each with 512Mi of memory, reachable on port 80" — and Kubernetes continuously works to make reality match that description. If a copy crashes, it starts another. If a machine dies, it reschedules the work elsewhere. This is the single idea underneath everything else in this handbook: declare desired state, let a control loop reconcile it.

Kubernetes grew out of Google's internal cluster manager, Borg, and was open-sourced in 2014. It's now maintained by the Cloud Native Computing Foundation and runs on every major cloud provider, on bare metal, and on your laptop.

Why teams adopt it

Self-healing

Failed containers restart automatically; unhealthy nodes are drained and workloads rescheduled without manual intervention.

Declarative infrastructure

Your cluster's state lives in YAML files you can version, review, and diff — the same workflow you already use for code.

Portable

The same manifests run on AWS, GCP, Azure, or a homelab, avoiding hard lock-in to a single provider's APIs.

Built for scale

Bin-packs workloads across a fleet of machines and scales pod counts up or down as demand changes.

What Kubernetes is not

It's not a PaaS like Heroku — there's no single "deploy my app" button out of the box; you assemble that experience from primitives (or use a higher-level tool like Helm on top). It's not a service mesh, a CI system, or a database. It orchestrates containers; everything else is layered on top, often by other CNCF projects.

Terminology primer

Cluster — the set of machines Kubernetes manages. Node — a single machine (VM or bare metal) in that cluster. Pod — the smallest deployable unit, wrapping one or more containers. Manifest — a YAML/JSON file describing desired state. Control loop — a background process that reconciles actual state toward desired state.

Beginner · 02

Architecture

A cluster splits into two planes: the control plane, which makes global decisions, and worker nodes, which run your actual workloads. Understanding this split makes almost every later concept easier to reason about.

Control plane components

ComponentRole
kube-apiserverThe front door. Every kubectl command, controller, and kubelet talks to the cluster exclusively through this REST API. It validates and persists objects.
etcdA distributed key-value store holding the entire cluster state. If etcd is lost with no backup, the cluster's memory of itself is gone.
kube-schedulerWatches for newly created Pods with no assigned node and picks a node for them, based on resource requests, constraints, and affinity rules.
kube-controller-managerRuns the core control loops (Node, ReplicaSet, Endpoints, Job controllers, etc.) that reconcile actual state toward desired state.
cloud-controller-managerBridges the cluster to your cloud provider's APIs — provisioning load balancers, attaching volumes, labeling nodes with zone info.

Node components

ComponentRole
kubeletThe agent on every node. Registers the node with the API server and makes sure the containers described in assigned Pods are running and healthy.
kube-proxyMaintains network rules on each node so traffic to a Service's virtual IP gets routed to one of its backing Pods.
Container runtimeThe software that actually runs containers — containerd or CRI-O today, speaking the Container Runtime Interface (CRI).
Mental model

Think of the control plane as the "brain" that only ever writes desired state to etcd and reads current state back, and every controller and kubelet as an independent loop constantly asking "does reality match what's in etcd? If not, take one step toward it." Nothing talks directly to anything else — they only ever go through the API server.

Managed vs. self-hosted control planes

In production, most teams don't run their own control plane. Managed offerings — EKS (AWS), GKE (Google Cloud), and AKS (Azure) — operate the control plane for you and expose only the API endpoint, which removes an entire category of operational burden (etcd backups, control-plane upgrades, HA quorum) at the cost of some configurability.

Beginner · 03

Getting Started

You need two things to begin: a cluster to talk to, and kubectl, the CLI that talks to it. For learning, run a cluster locally rather than paying for cloud infrastructure.

Local cluster options

ToolBest for
kindRuns Kubernetes nodes as Docker containers. Fast, scriptable, great for CI and multi-node testing.
minikubeA full single/multi-node VM-based cluster with add-ons (dashboard, ingress) toggled with one flag. Great first cluster.
k3dRuns lightweight k3s in Docker. Very low resource footprint, popular for local dev loops.
Docker DesktopShips a single-node cluster behind a checkbox — the lowest-friction option if you already have it installed.
bash
# install kubectl (macOS example — see docs for your OS)
brew install kubectl

# spin up a local cluster with kind
brew install kind
kind create cluster --name learning

# verify kubectl can reach it
kubectl cluster-info
kubectl get nodes

Essential first commands

bash
# apply a manifest (create or update to match the file)
kubectl apply -f deployment.yaml

# list resources
kubectl get pods
kubectl get pods -o wide
kubectl get all -n my-namespace

# inspect one object in detail
kubectl describe pod my-pod-abc123

# stream logs
kubectl logs -f my-pod-abc123

# shell into a running container
kubectl exec -it my-pod-abc123 -- /bin/sh

# delete what a file describes
kubectl delete -f deployment.yaml
Tip

Set up shell autocompletion and the k alias early — alias k=kubectl plus source <(kubectl completion zsh) saves an enormous amount of typing over the life of a project.

kubectl config & contexts

kubectl reads connection info from ~/.kube/config. A single config file can hold credentials for many clusters, called contexts. Switching context switches which cluster your next command targets — a common source of "why did that apply to the wrong cluster" incidents, so always check before running destructive commands.

bash
kubectl config get-contexts
kubectl config current-context
kubectl config use-context production-cluster
Core Concepts · 04

Pods & the Object Model

A Pod is the smallest thing you deploy — one or more containers that share a network namespace (same IP, same port space) and can share storage volumes. Most Pods wrap exactly one container; multi-container Pods exist for tightly-coupled helper patterns, covered below.

yaml
apiVersion: v1
kind: Pod
metadata:
  name: hello-pod
  labels:
    app: hello
    tier: frontend
spec:
  containers:
    - name: hello
      image: nginxdemos/hello:latest
      ports:
        - containerPort: 80
      resources:
        requests:
          cpu: "100m"
          memory: "64Mi"
        limits:
          cpu: "250m"
          memory: "128Mi"

Every Kubernetes object manifest shares the same four top-level fields: apiVersion (which API schema), kind (what type of object), metadata (name, namespace, labels, annotations), and spec (the desired state you're declaring). Once created, the API server also populates a status field reflecting observed state — you never write status yourself.

Warning

You will rarely create bare Pods directly in real work. A Pod has no self-healing of its own — if its node dies, it is gone. Almost always create Pods indirectly through a controller (Deployment, StatefulSet, Job) that recreates them for you. Section 05 covers why.

Labels, selectors & namespaces

Labels are arbitrary key-value pairs attached to objects (app: hello, env: staging). Selectors are queries over those labels, and they're how Services find Pods, how Deployments know which Pods they own, and how you filter kubectl get output. Namespaces partition a cluster into virtual sub-clusters for organizing teams, environments, or applications — names only need to be unique within a namespace, not across the whole cluster.

bash
# create a namespace
kubectl create namespace payments

# filter by label
kubectl get pods -l app=hello,tier=frontend

# target a namespace explicitly
kubectl get pods -n payments

# see every namespace at once
kubectl get pods -A

Multi-container Pod patterns

Sidecar

A helper container running alongside the main one for its whole lifetime — a log shipper or service-mesh proxy like Envoy.

Init container

Runs to completion before app containers start — good for waiting on a dependency or seeding a shared volume.

Ambassador

Proxies network calls out of the Pod, so the app talks to localhost and the ambassador handles service discovery.

The Pod lifecycle

A Pod moves through phases: Pending (accepted, not yet scheduled or images not yet pulled) → Running (bound to a node, at least one container running) → Succeeded/Failed (all containers terminated). Restart behavior is governed by restartPolicy: Always (the default, used by Deployments), OnFailure (used by Jobs), or Never.

Core Concepts · 05

Deployments & ReplicaSets

A Deployment is the controller you'll use for almost every stateless workload. You describe a Pod template and a replica count; the Deployment creates and manages a ReplicaSet, which in turn creates and watches over that many Pod copies, replacing any that disappear.

yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: myregistry/web:1.4.2
          ports:
            - containerPort: 8080

Why the extra layer? A Deployment never touches Pods directly — it owns a ReplicaSet, and rolling out a new image creates a new ReplicaSet at the new version while scaling the old one down. That's what makes rollouts and rollbacks safe: the previous ReplicaSet (and its config) still exists, so reverting is just scaling it back up.

bash
# ship a new image
kubectl set image deployment/web web=myregistry/web:1.5.0

# watch the rollout
kubectl rollout status deployment/web

# something's wrong — undo it
kubectl rollout undo deployment/web

# roll back to a specific revision
kubectl rollout undo deployment/web --to-revision=3

# scale manually
kubectl scale deployment/web --replicas=6

Rolling update knobs

FieldWhat it controls
maxSurgeHow many Pods above the desired count can exist during a rollout (extra capacity while updating).
maxUnavailableHow many Pods can be unavailable during a rollout. Set to 0 for zero-downtime updates.
revisionHistoryLimitHow many old ReplicaSets to retain for rollback. Default is 10.
progressDeadlineSecondsHow long a rollout can make no progress before it's reported as failed.
Production note

Pair every Deployment with readiness probes (Section 10). Without one, the rollout controller considers a new Pod "ready" the instant its container process starts — often before the app has finished booting — and will happily route traffic to it or keep surging forward into a bad rollout.

Core Concepts · 06

Services & Networking

Pods are ephemeral and get new IPs every time they're recreated, so nothing should ever talk to a Pod IP directly. A Service gives a stable virtual IP and DNS name in front of a changing set of Pods, selected by label — and load-balances across them.

TypeExposesTypical use
ClusterIPAn internal-only virtual IP, cluster-wide.Default. Service-to-service traffic inside the cluster.
NodePortA static port (30000–32767) on every node's IP.Quick external access without a cloud load balancer, dev/test.
LoadBalancerA cloud provider's external load balancer, wired to the Service.Public-facing production endpoints on a cloud provider.
ExternalNameA DNS CNAME to an external service — no proxying.Pointing at a resource that lives outside the cluster, e.g. a managed database.
yaml
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
    - port: 80          # port the Service listens on
      targetPort: 8080  # port the container listens on

Every Service also gets a DNS name automatically via cluster DNS (CoreDNS): web.default.svc.cluster.local — or just web from within the same namespace. This is the standard way Pods discover each other; hardcoded IPs should never appear in application config.

Ingress: HTTP routing at the edge

Running one LoadBalancer Service per app gets expensive and unwieldy fast. An Ingress is a single entry point that routes HTTP(S) traffic to many Services based on hostname and path, handled by an Ingress controller you install (NGINX Ingress, Traefik, or a cloud-native one).

yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: storefront
                port:
                  number: 80
Newer alternative

The Gateway API is the CNCF's successor to Ingress — more expressive (traffic splitting, header-based routing) and less reliant on vendor-specific annotations. Ingress remains widely deployed and perfectly production-viable; reach for Gateway API on new clusters if your controller supports it.

NetworkPolicy: who can talk to whom

By default every Pod can reach every other Pod. A NetworkPolicy restricts that, acting as a namespace-scoped firewall matched by label selectors. Covered in depth alongside the rest of the security model in Section 12.

Core Concepts · 07

Configuration

Keep configuration out of your container images so the same image can run in dev, staging, and production. Kubernetes gives you two objects for this: ConfigMaps for non-sensitive values, Secrets for sensitive ones.

yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:
  LOG_LEVEL: "info"
  FEATURE_FLAGS: "checkout_v2=true,dark_mode=false"
---
apiVersion: v1
kind: Secret
metadata:
  name: web-secrets
type: Opaque
stringData:
  DATABASE_URL: "postgres://app:changeme@db.internal:5432/app"

Both can be consumed the same two ways: as environment variables, or mounted as files into the container filesystem.

yaml
spec:
  containers:
    - name: web
      image: myregistry/web:1.4.2
      envFrom:
        - configMapRef:
            name: web-config
        - secretRef:
            name: web-secrets
      volumeMounts:
        - name: tls
          mountPath: /etc/tls
          readOnly: true
  volumes:
    - name: tls
      secret:
        secretName: web-tls
Warning

A Kubernetes Secret is base64-encoded, not encrypted, by default — anyone who can read the object via the API can decode it trivially. Enable encryption at rest for etcd, restrict who can get/list Secrets via RBAC, and for anything truly sensitive consider an external secrets manager (see below).

External secret management

Production clusters commonly avoid storing raw secret values in Kubernetes at all, instead syncing them from a dedicated store — HashiCorp Vault, AWS Secrets Manager, or GCP Secret Manager — using the External Secrets Operator or provider-native CSI drivers. This centralizes rotation, auditing, and access control outside the cluster's blast radius.

Immutable ConfigMaps

Setting immutable: true on a ConfigMap or Secret prevents further edits, which protects against accidental changes and lets the kubelet skip watching it for updates — a small but real performance win on large clusters. The convention is to suffix the name with a content hash (e.g. via Kustomize) and roll out a new ConfigMap object rather than editing one in place.

Core Concepts · 08

Storage

Container filesystems are ephemeral by default — anything written disappears when the container restarts. Kubernetes' storage model solves this in layers: Volumes for basic sharing, PersistentVolumes for durable storage decoupled from any one Pod.

Volumes

A Volume is attached to a Pod (not a container) and outlives individual container restarts within that Pod, though not the Pod itself unless it's backed by durable storage. Common types: emptyDir (scratch space, wiped when the Pod is removed), hostPath (a path on the node — use sparingly, it ties you to that specific node), and configMap/secret (mounting config as files, as shown above).

PersistentVolumes & PersistentVolumeClaims

For storage that must outlive a Pod entirely — a database's data directory — use the PV/PVC abstraction. A PersistentVolume (PV) represents an actual piece of storage (an EBS volume, an NFS share). A PersistentVolumeClaim (PVC) is a request for storage that a Pod makes; Kubernetes binds it to a matching PV. This indirection means application manifests never need to know the underlying storage implementation.

yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 20Gi
---
# referenced from a Pod template:
volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data

StorageClasses & dynamic provisioning

In practice you rarely hand-create PVs. A StorageClass describes a "kind" of storage (SSD-backed, replicated, a specific cloud disk type) and a provisioner. When a PVC references one, the provisioner creates a matching PV on demand — this is dynamic provisioning, the default workflow on every managed cloud offering.

Access modeMeaning
ReadWriteOnceMounted read-write by a single node at a time (most block storage — EBS, PD, Azure Disk).
ReadOnlyManyMounted read-only by many nodes simultaneously.
ReadWriteManyMounted read-write by many nodes at once (needs a networked filesystem like NFS or EFS/Filestore).
ReadWriteOncePodMounted read-write by exactly one Pod cluster-wide — the strictest option, useful for storage that must never be double-attached.
Production note

PVCs are not automatically backed up. Deleting a PVC (or the namespace it lives in) can delete the underlying volume depending on the StorageClass's reclaimPolicy. Use Velero or your cloud provider's volume snapshot feature for real backups — see Section 15.

Core Concepts · 09

Specialized Workloads

Deployments cover stateless apps well, but three other controllers handle patterns Deployments can't.

StatefulSets

Use a StatefulSet when Pod identity matters — databases, message queues, anything where each replica needs a stable, predictable name and its own dedicated storage across restarts. Pods get ordinal names (db-0, db-1, db-2), stable network identities, and are created/scaled/terminated in order, one at a time by default — rather than the interchangeable, parallel Pods a Deployment manages.

yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db
  replicas: 3
  selector:
    matchLabels: { app: db }
  template:
    metadata:
      labels: { app: db }
    spec:
      containers:
        - name: postgres
          image: postgres:16
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
    - metadata: { name: data }
      spec:
        accessModes: ["ReadWriteOnce"]
        resources: { requests: { storage: 50Gi } }

volumeClaimTemplates is the key difference from a Deployment: each replica gets its own PVC, created automatically and re-attached to the same ordinal Pod across restarts, rather than one shared volume.

Production note

Running a database inside Kubernetes via a StatefulSet is common but not free — you take on backup automation, failover orchestration, and version upgrades yourself, usually via an operator (e.g. the Zalando or CloudNativePG Postgres operators) that encodes that operational knowledge. For many teams, a managed database (RDS, Cloud SQL) outside the cluster remains the pragmatic default, with Kubernetes reaching in over the network.

DaemonSets

A DaemonSet ensures exactly one copy of a Pod runs on every node (or a selected subset) — the pattern for node-level infrastructure: log collectors (Fluent Bit), metrics agents (node-exporter), CNI plugins, and storage drivers. As nodes are added to the cluster, the DaemonSet automatically schedules a copy onto them.

Jobs & CronJobs

A Job runs a Pod to completion — for one-off or batch work, retrying on failure up to a configured limit rather than restarting forever like a Deployment would. A CronJob wraps a Job template with a schedule, creating a new Job at each tick — the Kubernetes equivalent of cron.

yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-report
spec:
  schedule: "0 2 * * *"
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: report
              image: myregistry/report-gen:2.1
              args: ["--since=24h"]
Production · 10

Resources & Health Checks

This section is where clusters stop being demos and start being reliable. Two mechanisms matter most: telling the scheduler how much CPU/memory a container needs, and telling Kubernetes how to check whether it's actually working.

Requests & limits

A request is what the scheduler reserves for a container when picking a node — it's a guarantee. A limit is the hard ceiling the container is not allowed to exceed. Omitting requests means the scheduler has no idea how much room your Pod needs, which leads directly to noisy-neighbor problems and unpredictable evictions.

yaml
resources:
  requests:
    cpu: "250m"      # 0.25 of a core, guaranteed
    memory: "256Mi"
  limits:
    cpu: "500m"       # throttled beyond this
    memory: "256Mi"   # OOMKilled beyond this
Warning

CPU limits throttle (slow the container down); memory limits kill the container (OOMKilled) — there's no such thing as memory throttling. A common, deliberately safe pattern is setting requests.memory == limits.memory so memory behavior is fully predictable, while giving CPU more headroom between request and limit.

Quality of Service classes

Kubernetes derives a QoS class per Pod from its requests/limits, which determines eviction order under node pressure — BestEffort Pods are killed first, then Burstable, and Guaranteed last.

ClassHow you get it
GuaranteedEvery container sets requests equal to limits, for both CPU and memory.
BurstableAt least one container sets a request, but requests ≠ limits.
BestEffortNo requests or limits set at all — first to be evicted, avoid in production.

ResourceQuotas & LimitRanges

A ResourceQuota caps total resource consumption per namespace (useful for multi-tenant clusters where teams share capacity). A LimitRange sets default and min/max requests/limits for containers in a namespace that don't specify their own — a safety net against someone forgetting resources entirely.

Probes: liveness, readiness, startup

Probes are how Kubernetes learns whether your app is actually functioning, not just whether the process happens to be running.

ProbeQuestion it answersOn failure
LivenessIs the app still working, or deadlocked?Container is killed and restarted.
ReadinessIs the app ready to receive traffic right now?Pod is pulled out of Service endpoints (not killed).
StartupHas the app finished its (possibly slow) boot sequence?Liveness/readiness checks are held off until this passes.
yaml
containers:
  - name: web
    image: myregistry/web:1.4.2
    startupProbe:
      httpGet: { path: /healthz, port: 8080 }
      failureThreshold: 30
      periodSeconds: 2
    readinessProbe:
      httpGet: { path: /ready, port: 8080 }
      periodSeconds: 5
      failureThreshold: 3
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }
      periodSeconds: 10
      failureThreshold: 3
      timeoutSeconds: 2
Tip

Keep liveness checks dumb — "is the process able to respond at all" — not "can I reach the database." A liveness probe that fails when a downstream dependency is slow will restart a perfectly healthy container and can turn a partial outage into a total one. Save dependency checks for readiness.

Production · 11

Autoscaling

Kubernetes can scale along three independent axes: how many Pod replicas exist, how much CPU/memory each Pod is allotted, and how many nodes the cluster has.

Horizontal Pod Autoscaler (HPA)

Adjusts the replica count of a Deployment/StatefulSet based on observed metrics — CPU and memory by default, or custom/external metrics (queue depth, request latency) via an adapter like Prometheus Adapter or KEDA.

yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

Vertical Pod Autoscaler (VPA)

Adjusts a container's requests/limits over time based on observed usage, instead of (or in addition to) replica count. Running VPA in Auto mode alongside HPA on the same metric (CPU) is a conflict — the two will fight — so most teams run VPA in recommendation-only mode for right-sizing, or use it for workloads that can't scale horizontally at all.

Cluster Autoscaler / Karpenter

Adjusts the number of nodes. The classic Cluster Autoscaler adds nodes when Pods are unschedulable due to insufficient capacity, and removes underutilized nodes. Karpenter (originally AWS, now broader) is a newer, faster alternative that provisions right-sized nodes directly for pending Pods rather than picking from pre-defined node group shapes.

Production note

HPA needs headroom to scale into — if the cluster has no spare node capacity, new replicas sit Pending no matter how aggressive your HPA thresholds are. Pod-level and node-level autoscaling are a pair; deploying one without the other only solves half the problem.

Pod Disruption Budgets

A PodDisruptionBudget (PDB) caps how many Pods of a set can be voluntarily disrupted at once — during node drains, cluster upgrades, or the Cluster Autoscaler removing a node. It doesn't prevent involuntary disruptions like a node crashing.

yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 2      # or use maxUnavailable instead
  selector:
    matchLabels:
      app: web
Production · 12

Security

Kubernetes security is layered: who can call the API, what a Pod is allowed to do at runtime, and what traffic is allowed on the network. Skipping any one layer leaves a real gap.

RBAC — who can do what

Role-Based Access Control grants permissions via three pieces: a Role (or cluster-wide ClusterRole) listing allowed verbs on resources, and a RoleBinding (or ClusterRoleBinding) attaching that role to a user, group, or ServiceAccount.

yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: payments
  name: pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: payments
subjects:
  - kind: ServiceAccount
    name: ci-deployer
    namespace: payments
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

Every Pod runs as a ServiceAccount — if you don't specify one, it gets the namespace's default account, which by convention should be granted no permissions at all. Give each workload its own dedicated ServiceAccount scoped to exactly the API access it needs.

Pod-level hardening

yaml
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    fsGroup: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: web
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]

Cluster-wide, a Pod Security Admission controller enforces one of three standard profiles at the namespace level — privileged, baseline, or restricted — rejecting Pods that violate it, applied via a namespace label rather than a separate policy object.

yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/warn: restricted

NetworkPolicy — default-deny

The strongest starting posture is denying all traffic by default and explicitly allowing what's needed, rather than trying to enumerate what to block.

yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: payments
spec:
  podSelector: {}
  policyTypes: ["Ingress", "Egress"]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-api
  namespace: payments
spec:
  podSelector:
    matchLabels: { app: api }
  ingress:
    - from:
        - podSelector: { matchLabels: { app: web } }
      ports:
        - port: 8080
Warning

NetworkPolicy objects only take effect if your CNI plugin implements them. Some basic CNI setups silently ignore NetworkPolicy entirely — verify enforcement (Calico, Cilium, and most managed cloud CNIs support it) before relying on it as a control.

Supply chain

  • Scan images for known CVEs in CI (Trivy, Grype) before they reach a registry.
  • Pin images by digest (image: repo/app@sha256:…) rather than a mutable tag like latest, so what's running is exactly what was scanned.
  • Use admission control (Kyverno or OPA Gatekeeper) to enforce policies cluster-wide — block :latest tags, require resource limits, disallow privileged Pods.
Production · 13

Observability

Once you're running dozens of Pods across a handful of nodes, "just check the logs" stops working. Production clusters need the standard three pillars — metrics, logs, traces — plus Kubernetes-specific event visibility.

Metrics

metrics-server provides the lightweight CPU/memory numbers kubectl top and the HPA rely on. For anything beyond that — historical data, custom application metrics, alerting — the de facto standard is Prometheus scraping metrics endpoints, with Grafana for dashboards and Alertmanager for routing alerts. The kube-prometheus-stack Helm chart installs all three pre-wired with sane cluster dashboards.

bash
kubectl top nodes
kubectl top pods -n payments --sort-by=memory

Logs

Container stdout/stderr is captured by the container runtime and readable via kubectl logs, but that only covers what's currently running — logs from a deleted Pod are gone. Production clusters ship logs off-node to a central store using a node-level DaemonSet agent (Fluent Bit, Vector, or the cloud provider's native agent) forwarding to Loki, Elasticsearch, or a managed logging service.

Traces

For anything with more than one hop — a request crossing several microservices — metrics and logs alone can't show you where time went. Distributed tracing (OpenTelemetry instrumentation, exported to Jaeger or Tempo) stitches a single request's path across services into one timeline.

Events — Kubernetes' own audit trail

The API server records Events for almost everything that happens to an object — a scheduling failure, an image pull error, a probe failure. This is usually the fastest way to diagnose a broken Pod, and it's the first thing to check, before logs.

bash
kubectl describe pod my-pod-abc123   # Events section at the bottom
kubectl get events --sort-by=.lastTimestamp -n payments
Tip

Events are only retained for about an hour by default (--event-ttl on the API server). If you need historical event data, ship them out with a tool like kubernetes-event-exporter rather than relying on kubectl get events after the fact.

Deploy Strategies, Helm & GitOps

Deployment strategies

StrategyHow it worksTrade-off
Rolling updateGradually replaces old Pods with new ones (the Deployment default).Simple, no extra infra, but both versions serve traffic briefly.
Blue-greenDeploy the new version fully alongside the old, then flip a Service selector to cut over instantly.Instant rollback (flip back), but doubles resource usage during the switch.
CanaryRoute a small percentage of traffic to the new version, watch metrics, then ramp up.Lowest blast radius on a bad release, but needs traffic-splitting tooling.

Native Kubernetes only gives you rolling updates out of the box. Canary and blue-green in a robust, automated form typically come from a progressive-delivery controller like Argo Rollouts or Flagger, which can also automate rollback based on live metrics.

Helm — packaging manifests

Hand-writing every manifest works until you need the same app deployed to five environments with slightly different values. Helm packages a set of manifests as a templated chart, parameterized by a values.yaml file per environment.

bash
helm repo add bitnami https://charts.bitnami.com/bitnami
helm install my-redis bitnami/redis -f values-prod.yaml
helm upgrade my-redis bitnami/redis -f values-prod.yaml
helm rollback my-redis 2
helm history my-redis

An increasingly common alternative for teams that want plain YAML without a templating language is Kustomize — layering environment-specific patches over a shared base — built directly into kubectl via kubectl apply -k.

GitOps

GitOps flips the deployment direction: instead of CI pushing changes to the cluster, a controller running inside the cluster continuously pulls from a Git repository and reconciles the cluster to match it. Git becomes the single source of truth, every change is a reviewable commit, and drift between what's deployed and what's declared is detected and corrected automatically. Argo CD and Flux are the two dominant implementations.

Why teams adopt it

git revert becomes your rollback mechanism, cluster state is auditable through commit history, and no CI system needs standing write credentials to production — it only needs to open a pull request.

High Availability & Disaster Recovery

Spreading workloads for resilience

Replicas that all land on one node, or one availability zone, defeat the purpose of having replicas. Pod anti-affinity and topology spread constraints tell the scheduler to actively distribute Pods.

yaml
spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule
      labelSelector:
        matchLabels: { app: web }

Control plane HA

Production clusters run an odd number (typically 3 or 5) of control-plane nodes, each with its own etcd member, so the cluster survives losing one node without losing quorum. On managed Kubernetes (EKS/GKE/AKS) this is handled for you; self-managed clusters need kubeadm-style HA setup and careful etcd operations.

Backups

WhatHow
etcd (cluster state)etcdctl snapshot save on a schedule, stored off-cluster. Managed Kubernetes handles this for you.
Application objects & PVsVelero — backs up Kubernetes object manifests and can snapshot PersistentVolumes via the cloud provider's snapshot API, restorable into a fresh cluster.
Application data (databases)Application-level backups (pg_dump, snapshots) — a PV backup alone isn't a substitute for a tested database restore process.

Multi-zone and multi-region

Spreading nodes across availability zones within a region protects against a single zone's outage and is close to table stakes for production. Multi-region is a bigger step — it usually means running independent clusters per region behind global DNS or a global load balancer, since a single Kubernetes cluster spanning regions introduces too much cross-region latency into control-plane operations to be practical.

Production note

A DR plan you haven't tested is a hypothesis, not a plan. Regularly restore a Velero backup into a scratch cluster and confirm the application actually comes back up — the first real test of a backup should never be during an actual incident.

Production Readiness Checklist

A practical pass before calling a workload production-ready. Not exhaustive, but each item has caused a real outage somewhere when skipped.

Every workload

  • Resource requests and limits set on every container — no BestEffort Pods.
  • Readiness, liveness, and (for slow-booting apps) startup probes configured.
  • At least 2–3 replicas, spread across zones with topology spread constraints or anti-affinity.
  • A PodDisruptionBudget so voluntary disruptions can't take the whole workload down at once.
  • Images pinned by digest, scanned for CVEs in CI, never running as root.
  • Dedicated ServiceAccount with least-privilege RBAC — not the namespace default.
  • Graceful shutdown handled: the app traps SIGTERM and finishes in-flight requests within terminationGracePeriodSeconds.

Cluster-wide

  • Control plane runs with HA (3+ nodes) or is on a managed offering.
  • etcd backups on a schedule, stored off-cluster, restore path tested.
  • Velero (or equivalent) backing up application objects and volumes.
  • Cluster/node autoscaling in place with real headroom for HPA to scale into.
  • Default-deny NetworkPolicy baseline, with explicit allows layered on top.
  • Metrics, centralized logging, and alerting wired up — not just kubectl logs.
  • A tested upgrade path for both the control plane and node OS/kubelet versions.
  • Admission policy (Kyverno/Gatekeeper) enforcing the org's non-negotiables cluster-wide.
Tip

Treat this list as a starting baseline, not a finish line — the right bar depends on your workload's actual failure tolerance. A stateless internal tool and a payment API don't need the same rigor.

Debugging command reference

bash
# why is this Pod not scheduling / crashing?
kubectl describe pod <pod>

# logs from the crashed container, not the restarted one
kubectl logs <pod> --previous

# logs from one container in a multi-container Pod
kubectl logs <pod> -c <container>

# does the Service actually have healthy backends?
kubectl get endpoints <service>

# drop an ephemeral debug container into a running Pod (no shell in the image? no problem)
